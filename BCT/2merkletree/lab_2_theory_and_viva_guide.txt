Goal of the lab
---------------
Implement and analyze a Merkle Tree (Binary Hash Tree) data structure in Python to demonstrate:
  1. how individual transactions are hashed at the leaf level using SHA-256,
  2. how leaf nodes are recursively paired and hashed upwards to derive a single 32-byte Merkle Root,
  3. how tampering with a single transaction alters only its specific authentication path ($O(\log N)$ hashes) up to the root,
  4. how comparing Merkle Roots enables instantaneous, lightweight tamper detection across thousands of transactions,
  5. why Merkle Trees enable Light Clients (SPV nodes) to verify transaction inclusion efficiently without downloading full blocks.

The four tasks form one pipeline:

  Task 1: Compute hashes for the supplied set of transactions.
  Task 2: Construct the Merkle Tree programmatically and determine the Merkle Root.
  Task 3: Modify one transaction and recompute only the affected hash path and the new Merkle Root.
  Task 4: Compare the original and modified Merkle Roots and explain how a Merkle Tree supports
          efficient integrity verification.

Overall process
---------------
Step 1. Define a list of input transaction strings (e.g., $T_0, T_1, T_2, T_3$).
Step 2. Execute Task 1 (Leaf Hashing): Hash each raw transaction string using SHA-256 to create the leaf layer nodes:
        $H_0 = \text{SHA-256}(T_0)$, $H_1 = \text{SHA-256}(T_1)$, $H_2 = \text{SHA-256}(T_2)$, $H_3 = \text{SHA-256}(T_3)$.
Step 3. Execute Task 2 (Tree Construction):
        - Pair adjacent leaf nodes: $H_{01} = \text{SHA-256}(H_0 + H_1)$, $H_{23} = \text{SHA-256}(H_2 + H_3)$.
        - If the leaf count is odd, duplicate the last leaf node to form a balanced pair before hashing.
        - Combine intermediate hashes recursively layer-by-layer until a single root hash remains:
          $\text{Merkle Root} = \text{SHA-256}(H_{01} + H_{23})$.
Step 4. Execute Task 3 (Selective Recomputation):
        - Modify a single transaction (e.g., alter $T_1$ to $T_1'$).
        - Recompute ONLY the leaf hash $H_1'$ and the ancestral hashes along its path to the root:
          $H_{01}' = \text{SHA-256}(H_0 + H_1')$, $\text{Merkle Root}' = \text{SHA-256}(H_{01}' + H_{23})$.
        - Explicitly avoid re-hashing unaffected subtrees ($H_2$, $H_3$, $H_{23}$).
Step 5. Execute Task 4 (Verification & Comparison):
        - Compare $\text{Merkle Root}$ vs $\text{Merkle Root}'$.
        - Demonstrate that changing 1 character in $T_1$ yields a completely different Merkle Root.
        - Explain how Merkle Audit Paths allow verifying inclusion in $O(\log N)$ time and space.

What the examiner checks
  - Correct tree building logic: Proper pairing, concatenation order, and double-hashing (if Bitcoin format).
  - Handles odd leaves: Duplicates the last node correctly when leaf count is odd.
  - Selective recomputation ($O(\log N)$): Demonstrates updating *only* the affected branch path rather than rebuilding the entire tree from scratch.
  - SPV and Integrity knowledge: Clear explanation of Merkle proofs, light node mechanics, and log-time verification.

PART B - THEORY: WHAT A MERKLE TREE IS AND WHY IT EXISTS
==============================================================================

B.1 Definition
--------------
A Merkle Tree (invented by Ralph Merkle in 1979) is a complete binary tree where:
- Every **Leaf Node** contains the cryptographic hash of a data block (transaction).
- Every **Non-Leaf (Internal) Node** contains the cryptographic hash of the concatenation of its child nodes' hashes.
- The **Root Node (Merkle Root)** is the single top-level hash that cryptographically summarizes all data in the tree.

B.2 The Core Problem Merkle Trees Solve in Blockchain
------------------------------------------------------
Consider a block containing 4,000 transactions:
1. Without a Merkle Tree: To verify if a single transaction is inside a block, a light client would have to download all 4,000 transactions (~1-2 MB per block), consuming huge network bandwidth and storage.
2. With a Merkle Tree: The block header only stores a single 32-byte **Merkle Root**. A light client needs only the target transaction plus $\log_2(N)$ sibling hashes (a **Merkle Proof**) to verify inclusion locally in microseconds!

B.3 Complexity Comparison
-------------------------

| Operation | Flat Hash Array / Linear Search | Merkle Tree |
| :--- | :--- | :--- |
| **Inclusion Verification Time** | $O(N)$ | $O(\log_2 N)$ |
| **Data Downloaded for Proof** | $O(N)$ (Full block data) | $O(\log_2 N)$ (Sibling hashes) |
| **Tamper Detection Effort** | $O(N)$ | $O(1)$ (Compare 32-byte Root) |
| **Selective Branch Update** | $O(N)$ | $O(\log_2 N)$ |

For a block with 4,096 transactions:
- Linear search requires downloading and hashing all **4,096** transactions.
- Merkle proof requires downloading only $\log_2(4096) = \mathbf{12}$ **hashes** (~384 bytes)!

PART C - TASK 1: LEAF HASHING AND TRANSACTION PREPROCESSING
==============================================================================

C.1 Leaf Generation Process
---------------------------
Given a sequence of transactions $T = [T_0, T_1, T_2, T_3]$:
1. Convert each transaction object or string into UTF-8 bytes.
2. Apply SHA-256 to each transaction to obtain the leaf layer hashes $L$:

$$H_i = \text{SHA-256}(T_i)$$

In Bitcoin implementation (Double SHA-256):
$$H_i = \text{SHA-256}(\text{SHA-256}(T_i))$$

C.2 Data Formatting Consistency
-------------------------------
To ensure deterministic hashing:
- Strings must be consistently encoded (e.g., UTF-8).
- Dictionaries/JSON transactions must sort keys (`json.dumps(tx, sort_keys=True)`).
- Hexadecimal strings must be concatenated correctly before computing parent node hashes.


==============================================================================
PART D - TASK 2: TREE CONSTRUCTION ALGORITHM AND MERKLE ROOT COMPUTATION
==============================================================================

D.1 Recursive Tree Building Algorithm
-------------------------------------
1. Input: List of leaf node hashes $L = [H_0, H_1, H_2, \dots, H_{N-1}]$.
2. Base Case: If $\text{length}(L) == 1$, return $L[0]$ as the **Merkle Root**.
3. Odd Leaf Adjustment: If $\text{length}(L)$ is odd, duplicate the last hash $L[-1]$ and append it to $L$ so that every node has a sibling.
4. Pair Processing: Iterate through $L$ in steps of 2 ($i = 0, 2, 4 \dots$):
   - Concatenate left child hex string and right child hex string: $\text{Combined} = L[i] + L[i+1]$.
   - Compute parent hash: $H_{\text{parent}} = \text{SHA-256}(\text{Combined})$.
   - Append $H_{\text{parent}}$ to a new parent level list $P$.
5. Recursion: Repeat step 2 using parent list $P$ as the new input list until only 1 hash remains.

D.2 Visual Tree Topology (4 Transactions)
------------------------------------------

```
                     Merkle Root (H_0123)
                   = SHA-256(H_01 + H_23)
                        /          \
                       /            \
                      /              \
               H_01                      H_23
       = SHA-256(H_0 + H_1)      = SHA-256(H_2 + H_3)
          /            \            /            \
         /              \          /              \
     H_0                H_1    H_2                H_3
   = H(T_0)           = H(T_1) = H(T_2)           = H(T_3)
      |                  |      |                  |
   [ Tx 0 ]           [ Tx 1 ] [ Tx 2 ]           [ Tx 3 ]
```

PART E - TASK 3: TRANSACTION TAMPERING AND SELECTIVE PATH RECOMPUTATION ($O(\log N)$)
==============================================================================

E.1 The Concept of Selective Recomputation
------------------------------------------
When a single transaction $T_1$ is modified to $T_1'$:
- **Naive Approach (Inefficient)**: Re-hash all transactions $T_0 \dots T_N$ and rebuild the entire Merkle Tree from scratch ($O(N)$ complexity).
- **Optimal Merkle Approach (Selective Recomputation)**: Only update the specific node path from the modified leaf $H_1'$ straight up to the Merkle Root ($O(\log N)$ complexity). All sibling subtrees remain untouched.

E.2 Selective Path Update Steps (Modifying $T_1 \rightarrow T_1'$)
---------------------------------------------------------------
1. Recompute Leaf Hash: $H_1' = \text{SHA-256}(T_1')$.
2. Recompute Level 1 Parent: $H_{01}' = \text{SHA-256}(H_0 + H_1')$.
   *(Notice: $H_0$ is read from memory; it is NOT recomputed from $T_0$! $H_2, H_3, H_{23}$ are completely ignored!)*
3. Recompute Level 2 Root: $\text{Merkle Root}' = \text{SHA-256}(H_{01}' + H_{23})$.
   *(Notice: $H_{23}$ is read directly from memory!)*

Total Hash Computations Required for 4 Leaves:
- Full Rebuild: 7 hash operations.
- Selective Path Recomputation: **2 hash operations** ($H_1'$ and $H_{01}'$, plus root combine).


==============================================================================
PART F - TASK 4: COMPARING MERKLE ROOTS AND EFFICIENT INTEGRITY VERIFICATION
==============================================================================

F.1 Instantaneous Tamper Detection ($O(1)$ Root Check)
------------------------------------------------------
Because SHA-256 exhibits the **Avalanche Effect**:
- Changing even 1 cent in $T_1$ changes $H_1'$ completely.
- Changing $H_1'$ changes $H_{01}'$ completely.
- Changing $H_{01}'$ changes $\text{Merkle Root}'$ completely.

By comparing the original stored 32-byte $\text{Merkle Root}$ with a newly calculated $\text{Merkle Root}'$:
- If $\text{Merkle Root} == \text{Merkle Root}' \implies$ ALL transactions in the block are guaranteed to be 100% authentic and un-tampered.
- If $\text{Merkle Root} \neq \text{Merkle Root}' \implies$ At least one transaction inside the block has been modified or corrupted.

F.2 Merkle Trees in Block Headers
---------------------------------
In Bitcoin and Ethereum block headers, blocks do NOT store raw transaction arrays in their header metadata. Block headers store ONLY:
- `previous_block_hash` (32 bytes)
- `merkle_root` (32 bytes)
- `timestamp`, `bits/target`, `nonce`

This keeps the block header fixed at just **80 bytes** (Bitcoin), allowing miners and full nodes to validate and gossip chain headers rapidly across P2P networks.

G.1 Complete Python Script (`lab2_merkle_tree.py`)

```python
import hashlib

def sha256(data_str):
    """Utility helper to compute SHA-256 hex digest of string input."""
    return hashlib.sha256(data_str.encode('utf-8')).hexdigest()

class MerkleTree:
    def __init__(self, transactions):
        self.transactions = transactions
        self.leaf_hashes = [sha256(tx) for tx in transactions]
        self.tree_levels = []
        self.build_tree()

    def build_tree(self):
        """Constructs the complete Merkle Tree layer by layer."""
        current_level = list(self.leaf_hashes)
        self.tree_levels = [current_level]

        while len(current_level) > 1:
            # Handle odd number of leaves by duplicating the last node
            if len(current_level) % 2 != 0:
                current_level.append(current_level[-1])

            next_level = []
            for i in range(0, len(current_level), 2):
                left = current_level[i]
                right = current_level[i+1]
                parent = sha256(left + right)
                next_level.append(parent)

            self.tree_levels.append(next_level)
            current_level = next_level

    def get_merkle_root(self):
        return self.tree_levels[-1][0] if self.tree_levels else None

    def update_transaction(self, index, new_tx):
        """Task 3: Selectively recomputes ONLY the affected path."""
        print(f"\n--- SELECTIVE PATH RECOMPUTATION FOR TX INDEX {index} ---")
        self.transactions[index] = new_tx
        new_leaf = sha256(new_tx)
        print(f"Old Leaf Hash [{index}]: {self.tree_levels[0][index]}")
        print(f"New Leaf Hash [{index}]: {new_leaf}")

        self.tree_levels[0][index] = new_leaf

        # Traversal up the tree recomputing ONLY affected parent nodes
        curr_idx = index
        for level in range(len(self.tree_levels) - 1):
            level_nodes = self.tree_levels[level]
            # Ensure even length pairing
            if len(level_nodes) % 2 != 0:
                level_nodes.append(level_nodes[-1])

            is_left = (curr_idx % 2 == 0)
            sibling_idx = curr_idx + 1 if is_left else curr_idx - 1

            left_hash = level_nodes[curr_idx] if is_left else level_nodes[sibling_idx]
            right_hash = level_nodes[sibling_idx] if is_left else level_nodes[curr_idx]

            parent_hash = sha256(left_hash + right_hash)
            parent_idx = curr_idx // 2

            print(f"Level {level} -> {level+1} Recomputed Parent [{parent_idx}]: {parent_hash}")
            self.tree_levels[level+1][parent_idx] = parent_hash
            curr_idx = parent_idx


# Demonstration Pipeline
if __name__ == "__main__":
    tx_list = [
        "Tx0: Alice->Bob:10",
        "Tx1: Bob->Charlie:5",
        "Tx2: Charlie->Dave:2",

    ]

    print("=================================================")

    print("=================================================")
    tree = MerkleTree(tx_list)

    print("Transactions:")
    for i, tx in enumerate(tx_list):
        print(f"  [{i}] {tx} => Hash: {tree.leaf_hashes[i]}")

    original_root = tree.get_merkle_root()
    print(f"\nCalculated Original Merkle Root: {original_root}")

    print("\n=================================================")
    print("TASK 3: MODIFY TRANSACTION & SELECTIVE UPDATE")
    print("=================================================")
    # Modify Tx1: Change 5 BTC to 500 BTC
    tampered_tx = "Tx1: Bob->Charlie:500"
    tree.update_transaction(1, tampered_tx)

    modified_root = tree.get_merkle_root()

    print("\n=================================================")

    print("=================================================")
    print(f"Original Root : {original_root}")

PART H - THEORY: SPV (SIMPLE PAYMENT VERIFICATION) AND MERKLE INCLUSION PROOFS
==============================================================================

H.1 What is SPV (Light Client)?
-------------------------------
A **Simplified Payment Verification (SPV)** node (such as a mobile wallet) does NOT download full blocks (which are gigabytes in size).
Instead, SPV nodes download ONLY block headers (80 bytes per block).

H.2 How Merkle Inclusion Proof Works
------------------------------------
Suppose a mobile wallet wants to verify if transaction $T_1$ ("Bob->Charlie:5") was included in Block #500,000.

1. SPV node requests a **Merkle Audit Path (Proof)** for $T_1$ from a full node.
2. Full node sends ONLY:
   - Target Transaction $T_1$
   - Sibling Hash $H_0$
   - Sibling Hash $H_{23}$
3. SPV Node locally computes:
   - $H_1 = \text{SHA-256}(T_1)$
   - $H_{01} = \text{SHA-256}(H_0 + H_1)$
   - $\text{Calculated Root} = \text{SHA-256}(H_{01} + H_{23})$
4. SPV Node compares $\text{Calculated Root}$ against the trusted `merkle_root` stored in its local 80-byte block header.
5. If match == `True`, transaction is cryptographically proven to be included in the block!

```
  Data Needed by SPV Node to Verify T_1:
  - Target Tx: T_1
  - Sibling 1: H_0
  - Sibling 2: H_23
  - Trusted Root: Stored in local Block Header
```


==============================================================================
PART I - EDGE CASES: ODD NUMBER OF LEAVES, DUPLICATE HASH ATTACKS, AND CVE-2012-2459
==============================================================================

I.1 Handling Odd Leaf Counts
----------------------------
If a block contains an odd number of transactions (e.g., 3 transactions: $T_0, T_1, T_2$):
- $T_0$ pairs with $T_1 \rightarrow H_{01}$.
- $T_2$ has no pair.
- Bitcoin Specification Rule: Duplicate the last hash $H_2$ so that it pairs with itself ($H_{22} = \text{SHA-256}(H_2 + H_2)$).

I.2 CVE-2012-2459 Vulnerability (Bitcoin Merkle Duplicate Vulnerability)
------------------------------------------------------------------------
Because Bitcoin duplicates the last hash when leaf count is odd:
- An attacker can craft a block where $[T_0, T_1, T_2]$ produces the EXACT same Merkle Root as a block with 4 transactions $[T_0, T_1, T_2, T_2]$.
- This creates potential 64-character hash collision ambiguity.
- Mitigation: Modern nodes check that block transaction lists do not contain duplicate tail transactions.

PART J - COMMON MISTAKES AND EXAMINER FOCUS
==============================================================================

Common Mistakes
---------------
1. Rebuilding the entire tree from scratch ($O(N)$) during Task 3 rather than executing selective path recomputation ($O(\log N)$).
2. Swapping left and right concatenation order when recomputing parent hashes (e.g., doing $H_1 + H_0$ instead of $H_0 + H_1$), which produces wrong parent hashes.
3. Failing to handle odd numbers of transactions, causing array index out-of-bounds errors.
4. Confusing Merkle Tree with Merkle DAG (used in IPFS/Ethereum state trees) or Patricia Trie.
5. Assuming Merkle Proofs require downloading all transactions in the block.

Examiner Focus
--------------
- Correct Merkle Root Calculation: Verifying tree height, pairing, and hashing logic.
- Selective Recomputation Demonstration: Explaining why only $\log_2(N)$ node evaluations are executed when 1 transaction changes.
- SPV Reasoning: Clear explanation of how light clients use Merkle proofs to verify transactions in $O(\log N)$ space/time.
- Integrity Concepts: Demonstrating how the avalanche effect propagates a 1-bit leaf change to the root.

PART K - VIVA QUESTIONS WITH ANSWERS (EXHAUSTIVE)

------------------------- SECTION 1: MERKLE TREE FUNDAMENTALS ----------------

Q1. What is a Merkle Tree?
A. A binary hash tree where leaf nodes represent hashes of data items (transactions) and non-leaf parent nodes represent the cryptographic hash of their concatenated child node hashes, culminating in a single Merkle Root.

Q2. Who invented the Merkle Tree?
A. Ralph Merkle in 1979.

Q3. What is stored in a Merkle Tree leaf node?
A. The cryptographic hash of an individual transaction data payload ($\text{SHA-256}(\text{Tx})$).

Q4. What is a Merkle Root?
A. The single 32-byte top-level hash digest at the apex of a Merkle Tree that cryptographically summarizes all transactions within the tree.

Q5. What happens to the Merkle Root if a single transaction in the tree is modified?
A. Due to the avalanche effect, changing a single bit in any leaf transaction completely changes its hash, which changes every parent hash up the branch path, producing a completely different Merkle Root.

------------------------- SECTION 2: ALGORITHM & COMPUTATIONAL COMPLEXITY ----

Q6. What is the time complexity to verify transaction inclusion using a Merkle Proof?
A. $O(\log_2 N)$, where $N$ is the total number of transactions in the block.

Q7. What is the space complexity of a Merkle Inclusion Proof?
A. $O(\log_2 N)$ hashes (storing only sibling hashes along the path to the root).

Q8. How does a Merkle Tree handle an odd number of transactions at a tree level?
A. The last hash node in the odd layer is duplicated and paired with itself to complete the binary tree structure.

Q9. What is selective path recomputation in Task 3?
A. Updating *only* the specific sequence of $\log_2(N)$ parent node hashes along the path from the modified leaf to the root, rather than rebuilding all $N$ leaves and subtrees.

Q10. For a block with 1,024 transactions, how many hash evaluations are needed for a Merkle proof?
A. $\log_2(1024) = 10$ hash evaluations.

------------------------- SECTION 3: SPV & LIGHT CLIENTS ---------------------

Q11. What is an SPV Node?
A. Simplified Payment Verification node: a lightweight blockchain client (like a mobile wallet) that downloads only 80-byte block headers instead of full block transaction bodies.

Q12. How does an SPV node verify a transaction without downloading the full block?
A. It requests a Merkle Audit Proof (sibling hashes) for the target transaction from a full node, recomputes the root hash locally, and verifies if it matches the `merkle_root` in its trusted block header.

Q13. Can an SPV node detect if a full node sends a fake transaction in a Merkle proof?
A. Yes. If the transaction is fake or altered, the recomputed Merkle Root will not match the immutable `merkle_root` stored in the block header signed by miners.

------------------------- SECTION 4: BLOCKCHAIN INTEGRITY & SECURITY ---------

Q14. Where is the Merkle Root stored in Bitcoin?
A. Inside the 80-byte Bitcoin Block Header.

Q15. Why don't Bitcoin block headers store the entire list of transactions?
A. Storing only the 32-byte Merkle Root keeps the block header small (80 bytes), allowing fast network propagation, low bandwidth usage, and efficient header validation.

Q16. What is the difference between a Merkle Tree in Bitcoin and Ethereum?
A. Bitcoin uses a standard binary Merkle Tree for transactions; Ethereum uses a **Modified Merkle Patricia Trie (MPT)** to store transactions, receipts, and state balances for efficient key-value lookups and state updates.

Q17. What is a Merkle Proof?
A. The minimal set of sibling node hashes required to reconstruct the path from a specific leaf node up to the Merkle Root.

------------------------- SECTION 5: ADVANCED & EDGE CASES -------------------

Q18. What is CVE-2012-2459 in Bitcoin?
A. A vulnerability where duplicating the last node for odd-length trees allowed attackers to create two different transaction lists that produced identical Merkle Roots.

Q19. What is double SHA-256 hashing in Bitcoin Merkle Trees?
A. Bitcoin hashes node data twice: $\text{SHA-256}(\text{SHA-256}(\text{data}))$, to protect against length extension attacks on SHA-256.

Q20. What is the height of a Merkle Tree with $N$ leaves?
A. $\lceil \log_2(N) \rceil + 1$.

Q21. Why is checking Merkle Root equivalence considered an $O(1)$ operation?
A. Because it involves comparing two fixed 32-byte hash strings regardless of how many millions of transactions are represented by the root.

Q22. Can an attacker replace a transaction in the middle of a Merkle tree without changing the Merkle Root?
A. No. Due to the collision resistance and pre-image resistance of SHA-256, it is computationally impossible to find a substitute transaction that yields the exact same root hash.
