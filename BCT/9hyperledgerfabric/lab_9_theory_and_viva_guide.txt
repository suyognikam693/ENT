Goal of the lab
---------------
Operate, analyze, execute transactions on, and troubleshoot a preconfigured Hyperledger Fabric test 
network (such as `test-network` with `asset-transfer-basic` chaincode written in Go, Node.js, or Java) to demonstrate:

  3. how asset attributes (owner, value, status) are updated in the CouchDB/LevelDB World State database and appended to the ledger,

  Task 2: Create/query a supplied asset using the provided chaincode/application/CLI interface.
  Task 3: Update or transfer the asset and verify the changed ledger/world-state information.
  Task 4: Explain and demonstrate the transaction path as Proposal → Endorsement → Ordering →

Step 2. Identify active network nodes: Orderer (`orderer.example.com`), Org1 Peer (`peer0.org1.example.com`),

Step 6. Task 4 Execution (Transaction Architecture & Troubleshooting):
        - Trace transaction lifecycle logs across Peer and Orderer containers.
        - Demonstrate the 5-step flow: Client sends proposal -> Endorsers simulate and sign -> Orderer packages into block -> Peers validate Read-Write set -> Block committed to ledger.
        - Troubleshoot examiner faults:
          * Fault A (Endorsement Policy Mismatch): Submitting transaction signed by only 1 org when policy requires `AND('Org1MSP.peer', 'Org2MSP.peer')`.
          * Fault B (Read-Write Set / MVCC Conflict): Submitting concurrent updates to the same key.

PART B - THEORY: PERMISSIONED BLOCKCHAINS AND HYPERLEDGER FABRIC ARCHITECTURE
==============================================================================

B.1 Public vs. Permissioned Blockchains
---------------------------------------
- **Public Blockchains (Bitcoin, Ethereum)**: Permissionless, anonymous nodes, public data visibility, Proof-of-Work / Proof-of-Stake consensus, execution of code on ALL nodes.
- **Permissioned Enterprise Blockchains (Hyperledger Fabric)**: Identified participants (PKI/MSP), access-controlled channels, confidential data, Execute-Order-Validate paradigm, high throughput (thousands of TPS), zero cryptocurrency/gas fees.

B.2 Key Hyperledger Fabric Components
-------------------------------------
1. Peers (`peer0.org1.example.com`): Nodes that host ledgers and chaincode.
   - Endorsing Peers: Simulate transaction proposals and sign endorsement responses.
   - Committing Peers: Validate transaction read-write sets and commit blocks to the ledger.
2. Orderer Nodes (`orderer.example.com`): Form the Ordering Service. Sort transactions chronologically, package them into blocks, and distribute blocks to peers. (Uses Raft consensus).
3. Organizations (Orgs): Legal or administrative enterprise entities participating in the network.
4. Membership Service Provider (MSP): Cryptographic identity manager utilizing X.509 digital certificates to authenticate user and node roles within an Org.
5. Channels (`mychannel`): Private "sub-blockchains" connecting specific subset of Organizations for confidential data sharing.
6. Chaincode: Smart contracts written in Go, Node.js, or Java that define business logic and asset structures.

D.1 Structure of an Asset in Chaincode
---------------------------------------
In the standard `asset-transfer-basic` chaincode, an Asset is represented as a JSON object:

```json
{
  "ID": "asset7",
  "Color": "blue",
  "Size": 5,
  "Owner": "Alice",
  "AppraisedValue": 300
}
```

D.2 Read Operation: Querying Assets (`peer chaincode query`)
-----------------------------------------------------------
Read-only queries execute locally on the target peer. They read from World State (CouchDB), do NOT submit transactions to the Orderer, do NOT consume block space, and return data instantly.

1. Query All Assets:
```bash
peer chaincode query \
  -C mychannel \
  -n basic \
  -c '{"Args":["GetAllAssets"]}'
```

2. Read Specific Asset (`asset7`):
```bash
peer chaincode query \
  -C mychannel \
  -n basic \
  -c '{"Args":["ReadAsset","asset7"]}'
```

D.3 Write Operation: Creating a New Asset (`peer chaincode invoke`)
------------------------------------------------------------------
Creating an asset alters World State and requires an **Endorsed Transaction**:

```bash
peer chaincode invoke \
  -o localhost:7050 \
  --ordererTLSHostnameOverride orderer.example.com \
  --tls \
  --cafile $PWD/organizations/ordererOrganizations/example.com/orderers/orderer.example.com/msp/tlscacerts/tlsca.example.com-cert.pem \
  -C mychannel \
  -n basic \
  --peerAddresses localhost:7051 \
  --tlsRootCertFiles $PWD/organizations/peerOrganizations/org1.example.com/peers/peer0.org1.example.com/tls/ca.crt \
  --peerAddresses localhost:9051 \
  --tlsRootCertFiles $PWD/organizations/peerOrganizations/org2.example.com/peers/peer0.org2.example.com/tls/ca.crt \
  -c '{"Args":["CreateAsset","asset7","blue","5","Alice","300"]}'
```

Expected Output:
`Chaincode invoke result: status:200`

PART F - TASK 4: COMPLETE TRANSACTION FLOW (PROPOSAL → ENDORSEMENT → ORDERING → VALIDATION → COMMIT)
==============================================================================

Unlike Ethereum or Bitcoin, Hyperledger Fabric uses an **Execute-Order-Validate** design paradigm divided into 5 distinct sequential steps:

```
  CLIENT APPLICATION
      │
      ├───── 1. PROPOSAL (Sends signed Proposal to Endorsing Peers) ──────────────┐
      │                                                                           │
      │◄──── 2. ENDORSEMENT (Returns Executed Read-Write Sets + Signatures) ─────┤
      │                                                                           │
      ├───── 3. ORDERING (Submits Endorsed Envelope to Ordering Service) ────────┼────────┐
      │                                                                           │        │
      │                                                                           ▼        ▼
  [ PEER 1 (Org1) ]                                                       [ ORDERER SERVICE ]
  (Endorser)                                                               (Packages Blocks)
      │                                                                            │
      └────── 4. VALIDATION & 5. COMMIT ◄──────────────────────────────────────────┘
              (Checks Endorsement Policy & MVCC Read-Write Set -> Commits to Ledger)
```

------------------------------------------------------------------------------
STEP 1: PROPOSAL (Client → Endorsing Peers)
------------------------------------------------------------------------------
- Action: Client SDK constructs a Transaction Proposal containing: `ChaincodeID`, `Function Name`, `Input Arguments`, and Client Identity (`MSP Certificate + Signature`).
- Recipient: Sent to Endorsing Peers dictated by the channel's Endorsement Policy (e.g., `peer0.org1` and `peer0.org2`).

------------------------------------------------------------------------------
STEP 2: ENDORSEMENT (Execution & Simulation on Endorsers)
------------------------------------------------------------------------------
- Action: Endorsing peers simulate the transaction by executing the chaincode against their local copy of World State.
- Key Rule: NO updates are written to the database during this phase!
- Output: Endorser generates a **Read-Write Set (RWSet)**:
  * Read Set: Variables and versions read during execution.
  * Write Set: New key-value states to be updated.
- Endorser signs the proposal response (RWSet + Endorsement Signature) and returns it to the client.

------------------------------------------------------------------------------
STEP 3: ORDERING (Client → Ordering Service)
------------------------------------------------------------------------------
- Action: Client collects endorsement signatures from required peers. Once endorsement policy criteria are satisfied, client packages responses into a Transaction Envelope and sends it to the Ordering Service (`orderer.example.com`).
- Role of Orderer: Orderer does NOT inspect contract state or execute chaincode. It simply sorts transactions chronologically across all network channels and packages them into immutable blocks using Raft consensus.

------------------------------------------------------------------------------
STEP 4: VALIDATION (Ordering Service → All Committing Peers)
------------------------------------------------------------------------------
- Action: Orderer broadcasts the newly constructed block to ALL Committing Peers on the channel.
- Peer Validation Checks:
  1. Endorsement Policy Check: Verifies that the block contains sufficient valid endorsement signatures matching policy rules.
  2. MVCC Read-Write Set Check (Concurrency Control): Verifies that key versions in the Read Set have NOT changed in World State since execution simulation occurred. (Prevents Double-Spending / Concurrency Bugs).

------------------------------------------------------------------------------
STEP 5: COMMIT (State Update & Block Ledger Append)
------------------------------------------------------------------------------
- Action:
  * Valid Transactions: Peer applies Write Set changes to World State (CouchDB/LevelDB).
  * Invalid Transactions: Peer marks transaction as INVALID in the block (retains block record for audit trails), but does NOT apply Write Set to World State!
- Block appended permanently to local ledger blockchain file. Emits event to client application.

PART G - TASK 4 (CONTINUED): TROUBLESHOOTING ENDORSEMENT & POLICY FAULTS
==============================================================================

Task 4 requires diagnosing an examiner-introduced fault. Below are the 3 standard Fabric fault scenarios:

------------------------------------------------------------------------------
FAULT SCENARIO 1: ENDORSEMENT POLICY FAILURE (`ENDORSEMENT_POLICY_FAILURE`)
------------------------------------------------------------------------------
Symptom:
Invoking chaincode returns error: `Error: transaction submission failed: Endorsement policy failure`.

Diagnosis:
The channel endorsement policy requires endorsements from BOTH Org1 and Org2 (`AND('Org1MSP.peer', 'Org2MSP.peer')`), but the `peer chaincode invoke` command specified `--peerAddresses` for ONLY Org1.

Resolution Steps:
Modify the CLI invocation command to include peer addresses and TLS root certificates for BOTH Org1 and Org2 (`--peerAddresses localhost:7051 ... --peerAddresses localhost:9051 ...`). Re-run transaction.

------------------------------------------------------------------------------
FAULT SCENARIO 2: MVCC READ-WRITE SET CONCURRENCY CONFLICT (`MVCC_READ_CONFLICT`)
------------------------------------------------------------------------------
Symptom:
Transaction succeeds at ordering stage, but logs on peer show: `Transaction 0xabc... marked INVALID: MVCC_READ_CONFLICT`. World state is NOT updated.

Diagnosis:
Two transactions attempted to update `asset7` simultaneously. Transaction A modified `asset7` version from $V_1 \rightarrow V_2$ while Transaction B was in-flight. When Transaction B reached Validation (Step 4), its Read Set expected version $V_1$, causing a version mismatch.

Resolution Steps:
Client application must catch `MVCC_READ_CONFLICT`, fetch the updated version $V_2$ from World State, re-generate proposal, and re-submit transaction.

------------------------------------------------------------------------------
FAULT SCENARIO 3: MSP CERTIFICATE / IDENTITY UNAUTHORIZED (`ACCESS_DENIED`)
------------------------------------------------------------------------------
Symptom:
Command fails with: `access denied for [CreateAsset][mychannel]: client identity is not authorized`.

Diagnosis:
Environment variable `CORE_PEER_MSPCONFIGPATH` points to an expired certificate or an identity lacking administrative / writer privileges on `mychannel`.

Resolution Steps:
Re-export `CORE_PEER_MSPCONFIGPATH` pointing to valid user certificates (`Admin@org1.example.com/msp` or `User1@org1.example.com/msp`).

PART I - THEORY: WORLD STATE (COUCHDB/LEVELDB) VS. IMMUTABLE TRANSACTION LOG
==============================================================================

I.1 Dual Database Architecture in Fabric
----------------------------------------
Hyperledger Fabric maintains two distinct data stores on every committing peer:

1. Immutable Transaction Log (Blockchain Ledger):
   - Storage Engine: Append-only flat block files stored on disk.
   - Contents: Cryptographically linked blocks containing transaction envelopes, execution status (valid/invalid), and historical read-write sets.
   - Purpose: Provides complete audit trail of all historical activity since genesis.

2. World State Database (State Database):
   - Storage Engine: LevelDB (default embedded key-value store) or CouchDB (pluggable JSON document database).
   - Contents: Current latest value of all asset keys (e.g., `asset7 -> Owner: Bob`).
   - Purpose: Allows chaincode to execute fast state lookups without traversing historical blocks from genesis.

I.2 Why Use CouchDB Over LevelDB?
---------------------------------
- **LevelDB**: Fast key-value store, supports simple key lookups and range queries.
- **CouchDB**: Supports rich JSON content queries (e.g., "Find all assets where Color == 'Yellow' and Owner == 'Charlie'"), index optimization, and Web UI inspection.

PART J - COMMON MISTAKES AND EXAMINER FOCUS
==============================================================================

Common Mistakes
---------------
1. Confusing `peer chaincode query` with `peer chaincode invoke`. `query` is for read-only local state checks; `invoke` submits transactions to the Orderer.
2. Specifying only 1 peer in `invoke` commands when the Endorsement Policy requires signatures from 2 Organizations.
3. Environment Variable Context Errors: Executing Org1 commands while `CORE_PEER_ADDRESS` is pointing to Org2.
4. Forgetting that invalid transactions are STILL stored in the blockchain ledger file (marked as invalid) even though they fail to update World State.
5. Assuming Orderers execute chaincode logic (Orderers ONLY sort and package blocks!).

Examiner Focus
--------------
- Command Execution Precision: Correct syntax for chaincode invocation and JSON parameter encoding.
- Architecture Mastery: Thorough explanation of the 5 transaction stages (Proposal, Endorsement, Ordering, Validation, Commit).
- Data Model Differentiation: Explaining how World State differs from Block History.
- Diagnostic Proficiency: Identifying why an endorsement or policy failure occurred and fixing it live.

PART K - VIVA QUESTIONS WITH ANSWERS (EXHAUSTIVE)

------------------------- SECTION 1: HYPERLEDGER FABRIC ARCHITECTURE ----------

Q1. What is Hyperledger Fabric?
A. An open-source, permissioned enterprise blockchain framework utilizing modular architecture, identity management (MSP), channels for privacy, and chaincode smart contracts.

Q2. How does Fabric differ from public blockchains like Ethereum?
A. Fabric is permissioned (all participants have known identities via MSP), executes transactions before ordering (Execute-Order-Validate), uses no cryptocurrency or gas fees, and supports fine-grained privacy via channels.

Q3. What is a Channel in Fabric?
A. A private "sub-blockchain" communications overlay connecting specific organizations for confidential transaction processing.

Q4. What is a Membership Service Provider (MSP)?
A. A component that manages cryptographic identities (X.509 certificates) to authenticate user permissions and node roles within an organization.

Q5. What is Chaincode?
A. A smart contract written in Go, Node.js, or Java that runs in an isolated Docker container and implements business logic to manage asset states.

------------------------- SECTION 2: TRANSACTION FLOW (5 STAGES) -------------

Q6. What are the 5 main stages of a Hyperledger Fabric transaction?
A. 1. Proposal, 2. Endorsement, 3. Ordering, 4. Validation, 5. Commit.

Q7. What happens during the Endorsement stage?
A. Endorsing peers simulate the transaction proposal against their local World State, generate a Read-Write Set (RWSet), sign the proposal response, and return it to the client without updating the database.

Q8. What is the role of the Ordering Service?
A. Orderers receive endorsed transactions from clients, order them chronologically across channels, and package them into blocks using consensus (Raft). They do NOT execute chaincode or read state.

Q9. What two checks occur during the Validation stage on Committing Peers?
A. 1. Endorsement Policy Check (verifies required signatures are present). 2. MVCC Read-Write Set Check (verifies key versions have not changed since simulation).

Q10. What happens if a transaction fails the MVCC Read-Write Set check?
A. The transaction is marked as INVALID inside the block; its record is kept permanently on the blockchain ledger for auditability, but its Write Set is NOT applied to World State.

------------------------- SECTION 3: WORLD STATE & LEDGER --------------------

Q11. What is the difference between World State and the Blockchain Ledger in Fabric?
A. World State holds the CURRENT value of all assets (stored in CouchDB/LevelDB) for fast lookups; the Blockchain Ledger is an append-only log of historical block files containing all transaction history.

Q12. What database options are available for World State?
A. LevelDB (default embedded key-value store) and CouchDB (supports rich JSON queries).

Q13. What is a Read-Write Set (RWSet)?
A. Data generated during proposal simulation containing keys/versions read (Read Set) and new key-value pairs to be written (Write Set).

------------------------- SECTION 4: CLI & OPERATION -------------------------

Q14. What command is used to read data without creating an on-chain transaction?
A. `peer chaincode query`.

Q15. What command is used to execute a state-changing operation?
A. `peer chaincode invoke`.

Q16. What parameter specifies which channel to target in CLI commands?
A. `-C channel_name` (e.g., `-C mychannel`).

Q17. What parameter specifies which chaincode package to invoke?
A. `-n chaincode_name` (e.g., `-n basic`).

------------------------- SECTION 5: TROUBLESHOOTING & SECURITY --------------

Q18. What is an Endorsement Policy?
A. A rule defining which organizations must endorse (sign) a transaction proposal before it can be accepted into the ledger (e.g., `AND('Org1MSP.peer', 'Org2MSP.peer')`).

Q19. What causes an `MVCC_READ_CONFLICT` error?
A. Occurs when a transaction attempts to update a key whose state version was modified by another transaction while the first transaction was in-flight.

Q20. Do invalid transactions get deleted from Hyperledger Fabric?
A. No. Invalid transactions are permanently recorded in the ledger block for auditing purposes, but their state changes are ignored by World State.

Q21. What consensus algorithm does the Fabric Ordering Service use?
A. Raft consensus protocol (Crash Fault Tolerant / CFT).

Q22. What port does Org1 Peer 0 typically use in Fabric test-network?
A. Port `7051` (and Port `9051` for Org2 Peer 0).
