Goal of the lab
---------------
Build, analyze, and test a lightweight, working blockchain data structure in Python to demonstrate:
  1. how a Block structure packages metadata (`index`, `timestamp`, `data`, `previous_hash`, `hash`),
  2. how cryptographic hash linkage connects consecutive blocks into an append-only hash chain,

        - Append at least 3 subsequent blocks ($B_1, B_2, B_3$) using `add_block()`.

        - Iterate from index 1 to $N-1$, performing two mandatory cryptographic checks per block:
          * Check 1 (Self-Consistency): `current_block.hash == current_block.calculate_hash()`
          * Check 2 (Link Integrity): `current_block.previous_hash == previous_block.hash`

        - Modify data inside an earlier block (e.g., change $B_1$'s data from `"Alice pays Bob 10"` to `"Alice pays Bob 1000"`).
        - Rerun `is_chain_valid()`.
        - Confirm output: `Chain Valid: FALSE`.
        - Report the exact failure index and explain how $B_1$'s altered hash breaks $B_2$'s stored `previous_hash`.

What the examiner checks

  - Stored Hash vs Computed Property: Hash is computed and stored at creation time (not dynamically computed on demand).
  - Validation Completeness: Both Check 1 (Self-Check) AND Check 2 (Linkage Check) are present in the validation loop.
  - Genesis Loop Bounds: Validation loop correctly starts at index 1 (`range(1, len(chain))`), avoiding index out-of-bounds or `-1` wraparound bugs.
  - Cascade Explanation: Demonstrating how modifying Block $K$ invalidates all subsequent blocks $K+1 \dots N$.

PART B - THEORY: WHAT A BLOCKCHAIN IS AND ITS FUNDAMENTAL DATA ARCHITECTURE
==============================================================================

B.1 Definition
--------------
A blockchain is an append-only, tamper-evident distributed ledger composed of a linearly ordered sequence of blocks. 
Each block contains a batch of transaction data and the cryptographic hash digest of the preceding block's header, 
forming an unbroken chain of hash pointers back to the genesis block.

B.2 Key Security Properties
---------------------------
1. Immutability (Tamper Evidence): Historical transactions cannot be modified without altering their hash and breaking all downstream chain links.
2. Append-Only Ledger: New records are added strictly to the end of the chain (tip); past entries are never deleted or rewritten.
3. Cryptographic Binding: Every block's identity hash cryptographically commits to all prior transactions in the chain's history.
4. Auditing Transparency: Any participant can independently re-run the chain validation algorithm to verify full state integrity.

B.3 Blockchain vs. Traditional Linked List vs. Database
-------------------------------------------------------

| Feature | Database (SQL/NoSQL) | Linked List (Data Structure) | Blockchain (Hash Chain) |
| :--- | :--- | :--- | :--- |
| **Pointer Type** | Primary Keys / Indexes | Memory Addresses (`*next`) | Cryptographic Hashes (`previous_hash`) |
| **Operations Allowed** | Create, Read, Update, Delete (CRUD) | Insert, Delete, Update | Append-Only, Read |
| **Tamper Detection** | None (Admin can overwrite values) | None (Modifying node data breaks nothing) | Instant (Modifying node invalidates all later links) |
| **Trust Model** | Centralized Administrator | Single Memory Space | Decentralized Consensus / Cryptographic Proof |

PART C - TASK 1: BLOCK STRUCTURE DEFINITION AND HASH CALCULATION MECHANICS
==============================================================================

C.1 Required Fields in Block Structure
--------------------------------------
Every block in a standard hash chain contains five basic attributes:

  index          : Integer position of the block in the chain ($0, 1, 2, \dots$).
  timestamp      : Unix epoch timestamp or formatted time string recording creation time.
  data           : Transaction details, state payload, or string message.
  previous_hash  : The 64-character SHA-256 hash of the immediately preceding block.
  hash           : The 64-character SHA-256 hash of THIS block's header fields.

C.2 Calculating the Block Hash
------------------------------
The block hash is generated by serializing all payload attributes (EXCLUDING the `hash` field itself) into a single deterministic string and feeding it to SHA-256:

$$\text{Block Hash} = \text{SHA-256}(\text{index} + \text{timestamp} + \text{data} + \text{previous\_hash})$$

Python Implementation Rule:
- All non-string fields (`index`, `timestamp`) must be cast to strings.
- Dictionaries or JSON objects must be formatted with sorted keys (`json.dumps(data, sort_keys=True)`).
- Input strings must be UTF-8 byte-encoded before passing to `hashlib.sha256()`.

```python
def calculate_hash(self):
    # Serializing all header fields except self.hash
    block_string = f"{self.index}{self.timestamp}{self.data}{self.previous_hash}"
    return hashlib.sha256(block_string.encode('utf-8')).hexdigest()
```

C.3 Critical Design Requirement: Stored Hash Attribute
------------------------------------------------------
The `hash` must be calculated and stored as a static variable at block creation time:
- `self.hash = self.calculate_hash()`
- **Anti-Pattern Warning**: If `hash` is implemented as a dynamic computed Python `@property` getter, modifying `data` will cause `hash` to auto-recalculate on the fly! This makes a tampered block appear perpetually self-consistent, completely defeating tamper detection. Storing the hash locks in the commitment made at creation time.

PART D - TASK 2: BLOCKCHAIN INITIALIZATION, GENESIS BLOCK, AND HASH LINKAGE
==============================================================================

D.1 The Genesis Block (Block 0)
-------------------------------
The Genesis Block is the first block ever created in a blockchain network.
- Index: `0`
- Previous Hash: A fixed placeholder string of zeros (`"0"` or `"0"*64`) because no prior block exists.
- Creation: Hardcoded or constructed automatically when the `Blockchain` class is instantiated.

D.2 The Concept of Hash Linkage
-------------------------------
Hash linkage is the mechanism that binds blocks together. When a new block $B_k$ is created:
1. It queries the tip of the current chain: `last_block = self.chain[-1]`.
2. It sets its `previous_hash` equal to `last_block.hash`.
3. It computes its own hash $H_k$, which incorporates `previous_hash`.
4. It appends $B_k$ to `self.chain`.

$$\text{Linkage Constraint: } \text{Block}[k].\text{previous\_hash} == \text{Block}[k-1].\text{hash} \quad \forall k \ge 1$$

D.3 Visual Representation of a 4-Block Chain
---------------------------------------------

```
  +------------------+      +------------------+      +------------------+      +------------------+
  | BLOCK 0 (Genesis)|      | BLOCK 1          |      | BLOCK 2          |      | BLOCK 3          |
  | Index: 0         |      | Index: 1         |      | Index: 2         |      | Index: 3         |
  | PrevHash: "0"    |  <-- | PrevHash: H0     |  <-- | PrevHash: H1     |  <-- | PrevHash: H2     |
  | Data: "Genesis"  |      | Data: "A->B 10"  |      | Data: "B->C 5"   |      | Data: "C->D 2"   |
  | Hash: H0 (a1f3..)|      | Hash: H1 (7c9e..)|      | Hash: H2 (3d20..)|      | Hash: H3 (e84b..)|
  +------------------+      +------------------+      +------------------+      +------------------+
```

PART E - TASK 3: CHAIN VALIDATION LOGIC ($O(N)$ AUDIT PROTOCOL)
==============================================================================

E.1 The Validation Algorithm
----------------------------
To audit a blockchain, a validator loops sequentially through all blocks starting from index 1 to $N-1$ and performs two distinct verification checks per block.

```python
def is_chain_valid(self):
    for i in range(1, len(self.chain)):
        current = self.chain[i]
        previous = self.chain[i - 1]

        # CHECK 1: Self-Consistency (Data / Hash Integrity)
        if current.hash != current.calculate_hash():
            print(f"Validation Error at Block {i}: Stored hash does not match recomputed hash!")
            return False

        # CHECK 2: Link Integrity (Hash Pointer Verification)
        if current.previous_hash != previous.hash:
            print(f"Validation Error at Block {i}: Broken link! previous_hash does not match previous block's hash!")
            return False

    return True
```

E.2 Why BOTH Verification Checks Are Mandatory
----------------------------------------------

### Scenario A: Attacker modifies data only
- Attacker changes $B_1$'s data from `"A->B 10"` to `"A->B 1000"`.
- Attacker DOES NOT update $B_1$'s stored hash field.
- **Check 1 Fails at Block 1**: $B_1$'s stored hash (`7c9e...`) $\neq$ recomputed hash (`52d8...`).

### Scenario B: Attacker modifies data AND updates that block's hash
- Attacker changes $B_1$'s data AND updates $B_1$'s stored hash field to the new recomputed value (`52d8...`).
- $B_1$ passes Check 1!
- **Check 2 Fails at Block 2**: $B_2$'s stored `previous_hash` (`7c9e...`) $\neq$ $B_1$'s new stored hash (`52d8...`).

Conclusion: Neither check alone is sufficient. Check 1 catches local data tampering; Check 2 catches link breakage caused by patched local hashes.

PART F - TASK 4: TAMPER DETECTION, DATA MODIFICATION, AND THE CASCADE RIPPLE EFFECT
==============================================================================

F.1 The Cascade (Ripple) Effect Step-by-Step
--------------------------------------------
Suppose a blockchain contains 4 blocks ($B_0 \rightarrow B_1 \rightarrow B_2 \rightarrow B_3$). An attacker attempts to alter transaction data in $B_1$:

1. Initial Tamper: $B_1.\text{data}$ is changed.
2. SHA-256 Avalanche Effect: Re-evaluating SHA-256 on $B_1$ produces a completely different hash $H_1'$.
3. Local Failure: $B_1.\text{hash} \neq H_1'$ (Caught by Check 1).
4. If Attacker Repairs $B_1.\text{hash} = H_1'$:
   - $B_1$ passes Check 1.
   - However, $B_2.\text{previous\_hash}$ still holds the old hash $H_1$.
   - $B_2.\text{previous\_hash} \neq B_1.\text{hash}$ (Caught by Check 2 at Block 2).
5. If Attacker Repairs $B_2.\text{previous\_hash} = H_1'$:
   - Modifying $B_2.\text{previous\_hash}$ changes $B_2$'s header input string!
   - Therefore, $B_2$'s own hash changes from $H_2 \rightarrow H_2'$.
   - Now $B_3.\text{previous\_hash}$ ($H_2$) no longer matches $B_2$'s new hash ($H_2'$). Check 2 fails at Block 3!

Summary Rule:
Modifying a historical block $B_K$ invalidates $B_K$ AND breaks every single downstream block $B_{K+1}, B_{K+2}, \dots, B_N$. The earlier the modified block, the larger the cascade of invalidated downstream blocks.

F.2 Proof-of-Work & Distributed Network Defense
-----------------------------------------------
In an in-memory lab script without Proof-of-Work (PoW) or network consensus, a script can quickly loop through and re-hash all downstream blocks to forge a fully consistent modified chain.

Real blockchains prevent this through:
1. Proof-of-Work / Proof-of-Stake: Re-mining a single block requires solving a hard cryptographic puzzle. Re-mining $N-K$ downstream blocks requires massive, cost-prohibitive computation.
2. Distributed Peer Copies: Thousands of independent full nodes hold copies of the true ledger. A single node with a rewritten chain will be rejected by consensus because its chain tip differs from the honest network majority.

G.1 Complete Python Script (`lab3_blockchain.py`)
------------------------------------------------

```python
import hashlib
import time
import json

class Block:
    def __init__(self, index, timestamp, data, previous_hash=""):
        self.index = index
        self.timestamp = timestamp
        self.data = data
        self.previous_hash = previous_hash
        self.hash = self.calculate_hash()

    def calculate_hash(self):
        """Computes SHA-256 digest over all header attributes."""
        # Ensure data is deterministically serialized if passed as dict
        data_str = json.dumps(self.data, sort_keys=True) if isinstance(self.data, dict) else str(self.data)
        payload = f"{self.index}{self.timestamp}{data_str}{self.previous_hash}"
        return hashlib.sha256(payload.encode('utf-8')).hexdigest()

class Blockchain:
    def __init__(self):
        self.chain = [self.create_genesis_block()]

    def create_genesis_block(self):
        """Generates initial Block 0."""
        return Block(0, "01/01/2026 00:00:00", "Genesis Block", "0")

    def get_latest_block(self):
        return self.chain[-1]

    def add_block(self, data):
        """Creates and appends a new block maintaining hash linkage."""
        prev_block = self.get_latest_block()
        new_index = prev_block.index + 1
        new_timestamp = time.strftime("%d/%m/%Y %H:%M:%S")
        new_block = Block(new_index, new_timestamp, data, prev_block.hash)
        self.chain.append(new_block)

    def is_chain_valid(self):
        """Audits full chain for self-consistency and link integrity."""
        for i in range(1, len(self.chain)):
            current = self.chain[i]
            previous = self.chain[i - 1]

            # Check 1: Verify current block data hasn't been altered
            if current.hash != current.calculate_hash():
                print(f"  [FAIL] Check 1 Failed at Block {i}: Stored hash [{current.hash[:10]}...] != Recomputed [{current.calculate_hash()[:10]}...]")
                return False

            # Check 2: Verify link to previous block is intact
            if current.previous_hash != previous.hash:
                print(f"  [FAIL] Check 2 Failed at Block {i}: Stored prev_hash [{current.previous_hash[:10]}...] != Actual prev hash [{previous.hash[:10]}...]")
                return False

        return True

    def print_chain(self):
        for block in self.chain:
            print(f"Block #{block.index}")
            print(f"  Timestamp: {block.timestamp}")
            print(f"  Data     : {block.data}")
            print(f"  Prev Hash: {block.previous_hash}")
            print(f"  Hash     : {block.hash}\n")


# Demonstration Pipeline
if __name__ == "__main__":
    print("=================================================")
    print("TASK 1 & 2: INITIALIZING BLOCKCHAIN & ADDING BLOCKS")
    print("=================================================")
    my_blockchain = Blockchain()
    my_blockchain.add_block("Alice pays Bob 10 BTC")
    my_blockchain.add_block("Bob pays Charlie 5 BTC")
    my_blockchain.add_block("Charlie pays Dave 2 BTC")

    my_blockchain.print_chain()

    print("=================================================")
    print("TASK 3: VALIDATING ORIGINAL UNTAMPERED CHAIN")
    print("=================================================")
    valid = my_blockchain.is_chain_valid()
    print(f"Is Original Blockchain Valid? => {valid}\n")

    print("=================================================")
    print("TASK 4: TAMPERING BLOCK 1 & DEMONSTRATING CASCADE")
    print("=================================================")
    print("Injecting Tamper: Modifying Block 1 Data to 'Alice pays Bob 1000 BTC'...")
    my_blockchain.chain[1].data = "Alice pays Bob 1000 BTC"

    print("Re-running Chain Validation...")
    valid_after_tamper = my_blockchain.is_chain_valid()
    print(f"Is Tampered Blockchain Valid? => {valid_after_tamper}\n")

    print("--- DEMONSTRATING ATTACKER RE-HASH PATCHING ---")
    print("Attacker manually re-computes Block 1's stored hash to bypass Check 1...")
    my_blockchain.chain[1].hash = my_blockchain.chain[1].calculate_hash()

    print("Re-running Chain Validation...")
    valid_after_patch = my_blockchain.is_chain_valid()
    print(f"Is Repaired-Hash Blockchain Valid? => {valid_after_patch}")
```

PART H - THEORY: HASH POINTERS, MERKLE ROOTS, AND CRYPTOGRAPHIC COMMITMENT
==============================================================================

H.1 What is a Hash Pointer?
---------------------------
A hash pointer is a data structure containing two components:
1. Memory/Storage Address: Where the referenced data is located.
2. Cryptographic Hash: The digest of the data at that location.

In a blockchain, `previous_hash` acts as a cryptographic hash pointer. It tells a node where the previous block is in sequence AND proves that its contents have not been modified.

H.2 Merkle Roots inside Block Headers
--------------------------------------
In production blockchains (Bitcoin, Ethereum), `data` is not stored as a plain string inside the block header. Instead:
- Hundreds of individual transactions are structured into a Merkle Tree.
- The 32-byte **Merkle Root** hash is placed into the block header.
- The block header hash then cryptographically commits to all transactions via the Merkle Root while keeping header size small.

PART I - EDGE CASES: INDEX CONTINUITY, DOUBLE TAMPERING, AND IN-MEMORY MUTABILITY
==============================================================================

I.1 Additional Validation Checks
--------------------------------
Beyond Check 1 (Self-hash) and Check 2 (Linkage), production validators execute additional structural checks:
1. Index Continuity Check: `block[i].index == block[i-1].index + 1`. Detects missing (deleted) or inserted blocks.
2. Genesis Block Check: `block[0] == KNOWN_GENESIS_BLOCK`. Prevents attackers from swapping out the origin block.
3. Timestamp Monotonicity Check: `block[i].timestamp >= block[i-1].timestamp`. Prevents time-travel block spoofing.

I.2 In-Memory Object Mutability Bug
-----------------------------------
In Python, objects are mutable by default. If a developer accidentally updates `block.data` and automatically updates `block.hash` via a setter or property getter, tamper detection fails! The hash must remain a static snapshot recorded at instantiation time.

PART J - COMMON MISTAKES AND EXAMINER FOCUS
==============================================================================

Common Mistakes
---------------
1. Leaving `previous_hash` out of the block's `calculate_hash()` string formulation. If `previous_hash` is omitted, blocks are hashed in isolation and the chain linkage is broken.
2. Leaving `data` out of the hash calculation, allowing data edits to occur without changing the block hash.
3. Starting the validation loop at index 0 (`range(0, len(chain))`), causing `chain[0-1]` to evaluate `chain[-1]` (the last block in Python), triggering a false validation bug.
4. Implementing `hash` as a dynamically computed Python property `@property` instead of storing it at block creation time.
5. Failing to test both failure points: showing what happens when data changes alone VS when data and stored hash are patched together.

Examiner Focus
--------------
- Code Inspection: Verifying that `index`, `timestamp`, `data`, and `previous_hash` are all hashed together.
- Hash Linkage Verification: Ensuring `new_block.previous_hash` explicitly pulls from `chain[-1].hash`.
- Validation Logic Precision: Confirming both Check 1 (hash equality) and Check 2 (link equality) are evaluated inside an $O(N)$ loop starting at index 1.
- Technical Explanation: Clear conceptual explanation of the cascade effect across downstream blocks.

PART K - VIVA QUESTIONS WITH ANSWERS (EXHAUSTIVE)
==============================================================================

------------------------- SECTION 1: BLOCKCHAIN FUNDAMENTALS -----------------

Q1. What is a blockchain?
A. An append-only, tamper-evident distributed ledger structured as an ordered sequence of blocks linked cryptographically by hash pointers.

Q2. What fields are contained in a standard block structure?
A. Index, timestamp, transaction data, previous block hash, and current block hash (plus nonce and difficulty target in PoW systems).

Q3. What is the Genesis Block?
A. The initial block of a blockchain (Index 0). It has no predecessor, so its `previous_hash` is set to a fixed placeholder like `"0"`.

Q4. How is a blockchain different from a standard linked list?
A. A linked list uses memory pointers where modifying node data breaks nothing; a blockchain uses cryptographic hash pointers where modifying node data invalidates all subsequent block hashes.

Q5. Is data in a public blockchain encrypted?
A. No. Blockchains provide integrity and authentication, not confidentiality. Data is hashed and publicly readable unless encrypted separately before inclusion.

------------------------- SECTION 2: HASH LINKAGE & CREATION -----------------

Q6. How is hash linkage established when adding a new block?
A. By setting the new block's `previous_hash` attribute directly to the stored `hash` of the preceding block (`chain[-1].hash`) before computing the new block's hash.

Q7. Which fields must be included in the input string of `calculate_hash()`?
A. All header fields that require integrity protection: index, timestamp, data, and previous hash (plus nonce if applicable). The current hash itself is excluded.

Q8. Why must `previous_hash` be included inside the input string when calculating a block's hash?
A. So that a block cryptographically commits to its predecessor. If `previous_hash` is omitted, the link between blocks can be altered without changing the block's own hash.

Q9. Why should a block's hash be stored at creation time rather than recomputed on demand?
A. Storing the hash locks in the commitment made at creation. If recomputed dynamically on demand, modifying block data would auto-update the hash, hiding the tamper during validation.

------------------------- SECTION 3: VALIDATION LOGIC ------------------------

Q10. What two primary checks are performed in a chain validation function?
A. Check 1 (Self-Consistency): Recomputed block hash matches stored block hash. Check 2 (Link Integrity): Current block's `previous_hash` matches previous block's stored `hash`.

Q11. Why does the validation loop start at index 1 instead of index 0?
A. Because Block 0 (Genesis) has no preceding block to compare links against. In Python, evaluating `chain[0-1]` accesses `chain[-1]` (the last block), causing a logic bug.

Q12. If an attacker modifies block data and updates its stored hash, which check catches the attack?
A. Check 2 (Link Integrity) fails at the *next* block because the next block's stored `previous_hash` still points to the old hash.

Q13. What is the time complexity of validating a blockchain of $N$ blocks?
A. $O(N)$, requiring one hash evaluation and link check per block.

------------------------- SECTION 4: TAMPER DETECTION & CASCADE EFFECT --------

Q14. What is the cascade (ripple) effect of tampering with an earlier block?
A. Modifying data in Block $K$ changes its SHA-256 digest, which invalidates Block $K$'s stored hash and breaks the `previous_hash` link in Block $K+1$. Repairing $K+1$ alters its hash, breaking $K+2$, propagating invalidation all the way to the chain tip.

Q15. Can an attacker rewrite a block in an in-memory Python blockchain script?
A. Yes, because in memory without Proof-of-Work, a script can re-hash all downstream blocks instantly. Real networks prevent this using Proof-of-Work cost and distributed multi-node consensus.

Q16. What happens if a block is deleted from the middle of the chain?
A. The index continuity check fails, and the link check fails because the block following the deleted block has a `previous_hash` pointing to the deleted block's hash.

------------------------- SECTION 5: ADVANCED CONCEPTS -----------------------

Q17. What is a hash pointer?
A. A structure storing both a data location pointer and the cryptographic SHA-256 hash of the data at that location, allowing data retrieval and instant integrity verification.

Q18. What is the role of Merkle Roots inside production block headers?
A. Instead of hashing raw transaction strings directly in the block header, transactions are structured into a Merkle Tree and the 32-byte Merkle Root is stored in the header, keeping headers lightweight.

Q19. How do distributed node copies prevent single-node ledger tampering?
A. If one node alters its local database, its chain tip hash will differ from the rest of the network. Under the majority consensus rule, honest nodes reject the tampered chain.

Q20. What is a block header vs a block body in Bitcoin?
A. Header contains metadata (version, prev hash, Merkle root, timestamp, bits, nonce); Body contains the complete list of transactions.

Q21. Why is SHA-256 ideal for blockchain hashing?
A. Because it is deterministic, one-way, collision-resistant, fast to evaluate, and exhibits a strong avalanche effect.

Q22. What does immutability mean in the context of blockchain technology?
A. Practical immutability: once data is buried under multiple blocks (confirmations), altering it requires re-doing astronomical amounts of computational work across a distributed network, making history practically unwriteable.
