PART B - THEORY: CRYPTOGRAPHIC HASH FUNCTIONS & SHA-256
==============================================================================

B.1 Definition
--------------
A Cryptographic Hash Function is a mathematical algorithm that maps an arbitrary block of data 
of any size to a fixed-size bit array (a digest). SHA-256 (Secure Hash Algorithm 256-bit) is a 
member of the SHA-2 family designed by the NSA, producing a 256-bit (32-byte) digest.

B.2 The Core Properties of SHA-256
----------------------------------
1. Deterministic: The exact same input data will always produce the exact same 256-bit hash output.
2. Fast Computation: Computing the hash of a message is computationally efficient ($O(N)$ time complexity).
3. Pre-image Resistance (One-Way Property): Given a hash digest $H$, it is computationally impossible 
   to reverse the algorithm to find the original input message $M$ such that $\text{SHA-256}(M) = H$.
4. Second Pre-image Resistance: Given an input $M_1$, it is computationally infeasible to find another distinct 
   input $M_2$ ($M_1 \neq M_2$) such that $\text{SHA-256}(M_1) = \text{SHA-256}(M_2)$.
5. Collision Resistance: It is computationally impossible to find ANY two distinct inputs $M_1$ and $M_2$ 
   that produce the same hash output ($\text{SHA-256}(M_1) = \text{SHA-256}(M_2)$).
6. Avalanche Effect: Changing a single bit in the input message (e.g., changing a period to a comma) 
   results in a completely different, uncorrelated hash output (typically flipping ~50% of output bits).

B.3 Structure of a SHA-256 Digest
---------------------------------
- Binary Output: 256 bits (zeros and ones).
- Hexadecimal Output: 64 hexadecimal characters (since $1 \text{ hex char} = 4 \text{ bits}$, $256 / 4 = 64$).
- Example Output: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` (Empty string hash).

PART C - THEORY: ASYMMETRIC CRYPTOGRAPHY & ELLIPTIC CURVES (ECDSA)
==============================================================================

C.1 Symmetric vs. Asymmetric Cryptography
-----------------------------------------
- **Symmetric Cryptography (AES, DES)**: Uses a single shared secret key for both encryption and decryption. Requires pre-sharing secret keys securely.
- **Asymmetric Cryptography (RSA, ECC)**: Uses a mathematically linked key pair:
  * Private Key ($d$): A secret random number kept strictly private by the owner. Used to generate digital signatures.
  * Public Key ($Q$): Derived mathematically from the private key. Distributed publicly to anyone. Used to verify signatures and derive wallet addresses.

C.2 Why Elliptic Curve Cryptography (ECC)?
-------------------------------------------
Traditional RSA cryptography requires huge 2048-bit or 4096-bit keys for strong security, which consumes 
excessive storage and bandwidth in blockchain ledgers.
ECC provides equivalent cryptographic security with much smaller key sizes:

| Algorithm | Key Size (Bits) | Equivalent Security Level | Relative Efficiency |
| :--- | :--- | :--- | :--- |
| **RSA** | 3072 bits | 128-bit security | Slow, large signatures |
| **ECC (ECDSA)** | 256 bits | 128-bit security | Fast, compact signatures |

C.3 Elliptic Curve Digital Signature Algorithm (ECDSA)
------------------------------------------------------
ECDSA is the cryptographic algorithm used in Bitcoin (Secp256k1), Ethereum (Secp256k1), and Hyperledger Fabric (P-256/Secp256r1) for authentication.

An Elliptic Curve over a finite field is defined by the algebraic equation:
$$y^2 = x^3 + ax + b \pmod p$$

For the **Secp256k1** curve used in Bitcoin/Ethereum:
- $a = 0$
- $b = 7$
- Equation: $y^2 = x^3 + 7 \pmod p$

PART E - TASK 2 & TASK 3: KEY PAIR GENERATION, DIGITAL SIGNING, AND VERIFICATION
==============================================================================

E.1 Digital Signing Process (Task 2)
-----------------------------------
Signing proves ownership of the private key without revealing the private key itself.

Mathematical Pipeline:
1. Message Payload $M$ is hashed: $H = \text{SHA-256}(M)$.
2. A cryptographically secure random integer $k$ (ephemeral nonce) is selected.
3. Private Key $d$ signs hash $H$ along with $k$ over the elliptic curve curve point $G$.
4. Output: Digital Signature tuple $(r, s)$.

$$\text{Signature } S = (r, s) = \text{ECDSA\_Sign}(d_{\text{private}}, \text{SHA-256}(M))$$

E.2 Signature Verification Process (Task 3)
------------------------------------------
Verification takes three inputs:
1. Original Message Payload $M$ (or its hash $H$).
2. Digital Signature $S = (r, s)$.
3. Sender's Public Key $Q_{\text{public}}$.

Mathematical Pipeline:
1. Verifier hashes the received message: $H' = \text{SHA-256}(M)$.
2. Verifier uses Public Key $Q_{\text{public}}$, signature $(r, s)$, and curve generator $G$ to calculate point $P = (x_P, y_P)$.
3. Verification Check: If $x_P \pmod n == r$, the signature is **VALID** (`True`).
4. Result: Proves that the owner of the matching private key signed this exact hash $H'$.

```
  [ SENDER (Private Key 'd') ]                     [ RECEIVER / VERIFIER (Public Key 'Q') ]
  Message (M) ──► SHA-256 ──► Hash (H)             Message (M) ──► SHA-256 ──► Hash (H')
                               │                                              │
                               ▼                                              ▼
                    Sign(d, H) ──► Signature (r, s) ──────────────────► Verify(Q, H', (r, s))
                                                                              │
                                                                              ▼
                                                                        Result: VALID (True)
```

PART F - TASK 4: TAMPERING, SIGNATURE FAILURE, INTEGRITY, AND NON-REPUDIATION
==============================================================================

F.1 Executing the Tamper Attack (Task 4)
----------------------------------------
1. Original Message $M_1$: `{"from": "Alice", "to": "Bob", "amount": 50}`
2. Signature $S_1$: Produced using Alice's Private Key $d_{\text{Alice}}$ on $M_1$.
3. Tampered Message $M_2$: `{"from": "Alice", "to": "Bob", "amount": 5000}` (Modified by an attacker).
4. Verification Call: `ECDSA_Verify(Q_{\text{Alice}}, \text{SHA-256}(M_2), S_1)`.
5. Result: **FAILED** (`False` or `BadSignatureError`).

F.2 Cryptographic Explanation of Failure
----------------------------------------
- $M_1 \neq M_2 \implies \text{SHA-256}(M_1) \neq \text{SHA-256}(M_2)$ due to the avalanche effect.
- Signature $S_1$ was calculated using hash $H_1 = \text{SHA-256}(M_1)$.
- When the verifier evaluates $S_1$ against hash $H_2 = \text{SHA-256}(M_2)$, the mathematical curve equality $x_P \pmod n == r$ fails.
- Therefore, the signature created for $M_1$ is mathematically invalid for $M_2$.

F.3 Three Core Blockchain Security Pillars
------------------------------------------
1. Data Integrity: Ensures transaction data cannot be altered in transit or at rest. Any tampering invalidates the signature.
2. Authentication: Confirms the identity of the transaction sender. Only the holder of the corresponding private key could have generated a valid signature for that public key.
3. Non-Repudiation: Prevents a sender from falsely claiming they did not initiate a transaction. Because only the sender possesses the private key, a valid signature serves as undeniable cryptographic proof of authorship.

G.1 Complete Python Implementation Script (`lab1_crypto_demo.py`)

```python
import hashlib
import json
import ecdsa

def main():
    print("=================================================")
    print("TASK 1: COMPUTE SHA-256 TRANSACTION HASH")
    print("=================================================")
    
    # Original Transaction Payload
    tx_original = {
        "sender": "0xAlice1234567890abcdef1234567890abcdef12",
        "receiver": "0xBob9876543210fedcba9876543210fedcba98",
        "amount": 50,
        "nonce": 1
    }

    # Deterministic JSON Serialization
    tx_string_orig = json.dumps(tx_original, sort_keys=True)
    tx_bytes_orig = tx_string_orig.encode('utf-8')

    # Compute SHA-256 Hash
    hash_orig = hashlib.sha256(tx_bytes_orig).hexdigest()

    print(f"Original Payload : {tx_string_orig}")
    print(f"SHA-256 Digest   : {hash_orig}")
    print(f"Digest Length    : {len(hash_orig)} hex characters ({len(hash_orig)*4} bits)\n")

    print("=================================================")
    print("TASK 2: KEY GENERATION & DIGITAL SIGNING")
    print("=================================================")

    # Generate ECDSA Key Pair using SECP256k1 curve (Bitcoin/Ethereum standard)
    private_key = ecdsa.SigningKey.generate(curve=ecdsa.SECP256k1)
    public_key = private_key.get_verifying_key()

    private_key_hex = private_key.to_string().hex()
    public_key_hex = public_key.to_string().hex()

    print(f"Private Key (Secret) : {private_key_hex}")
    print(f"Public Key (Identity): {public_key_hex}")

    # Sign the SHA-256 hash byte array using Private Key
    signature_bytes = private_key.sign(tx_bytes_orig)
    signature_hex = signature_bytes.hex()

    print(f"Digital Signature    : {signature_hex}")
    print(f"Signature Length     : {len(signature_hex)} hex characters ({len(signature_bytes)} bytes)\n")

    print("=================================================")
    print("TASK 3: SIGNATURE VERIFICATION (ORIGINAL DATA)")
    print("=================================================")

    try:
        # Verify signature against original data using Public Key
        is_valid = public_key.verify(signature_bytes, tx_bytes_orig)
        print(f"Verification Result  : SUCCESS -> Signature Valid? [{is_valid}]\n")
    except ecdsa.BadSignatureError:
        print("Verification Result  : FAILED -> Invalid Signature!\n")

    print("=================================================")
    print("TASK 4: TAMPERING DEMONSTRATION & FAILURE")
    print("=================================================")

    # Modify Transaction Payload (Tamper: Amount changed from 50 to 5000)
    tx_tampered = {
        "sender": "0xAlice1234567890abcdef1234567890abcdef12",
        "receiver": "0xBob9876543210fedcba9876543210fedcba98",
        "amount": 5000, # TAMPERED VALUE!
        "nonce": 1
    }

    tx_string_tamp = json.dumps(tx_tampered, sort_keys=True)
    tx_bytes_tamp = tx_string_tamp.encode('utf-8')
    hash_tamp = hashlib.sha256(tx_bytes_tamp).hexdigest()

    print(f"Tampered Payload : {tx_string_tamp}")
    print(f"Tampered Hash    : {hash_tamp}")

    print("\nAttempting to verify original signature against TAMPERED transaction...")
    try:
        public_key.verify(signature_bytes, tx_bytes_tamp)
        print("Verification Result  : UNEXPECTED SUCCESS (Security Breach!)")
    except ecdsa.BadSignatureError:
        print("Verification Result  : FAILED -> BadSignatureError Caught!")
        print("Cryptographic Proof  : Tampering detected! Signature matches original data ONLY.")

if __name__ == "__main__":
    main()
```

PART H - THEORY: MATHEMATICAL FOUNDATIONS OF SECP256K1 & ECDSA
==============================================================================

H.1 Private Key to Public Key Derivation
---------------------------------------
- Private Key ($d$): A 256-bit integer chosen randomly from the range $[1, n-1]$.
- Generator Point ($G$): A fixed, standardized coordinate point on the SECP256k1 curve.
- Public Key ($Q$): Point multiplication on the curve:

$$Q = d \times G$$

Crucial Security Property:
Computing $Q = d \times G$ is trivial via scalar point multiplication.
However, given $Q$ and $G$, computing $d = Q / G$ is the **Elliptic Curve Discrete Logarithm Problem (ECDLP)**, which is computationally intractable with classical computers.

H.2 ECDSA Signature Output Format
---------------------------------
An ECDSA signature consists of two 256-bit integers: $(r, s)$.
- $r$: The x-coordinate of the ephemeral point $k \times G \pmod n$.
- $s$: Calculated as $s = k^{-1} (H(M) + r \cdot d) \pmod n$.

Combined, $(r, s)$ forms a 64-byte signature array (or DER-encoded byte structure).

PART I - REAL-WORLD APPLICATIONS: BITCOIN ADDRESSES, ETHEREUM KEYS, AND UTXOS
==============================================================================

I.1 Deriving a Bitcoin / Ethereum Address
-----------------------------------------
1. Private Key ($d$): 256-bit random number.
2. Public Key ($Q$): $Q = d \times G$ (Uncompressed 65 bytes or Compressed 33 bytes).
3. Ethereum Address Derivation:
   - Take Keccak-256 hash of Public Key bytes (excluding 0x04 prefix).
   - Take the **last 20 bytes** (40 hex characters) of the hash.
   - Prepend `0x`. Example: `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`.

I.2 Unspent Transaction Outputs (UTXO) & Account Authorization
---------------------------------------------------------------
In Bitcoin: To spend a UTXO, the user provides a `ScriptSig` containing a valid ECDSA signature $(r, s)$ and their Public Key. Nodes execute `ScriptPubKey` to verify that the signature matches the public key hash storing the Bitcoin.

PART J - COMMON MISTAKES AND EXAMINER FOCUS
==============================================================================

Common Mistakes
---------------
1. Inconsistent Serialization: Formatting JSON strings without `sort_keys=True`, causing dictionary key ordering to change and altering hash outputs unpredictably.
2. Hashing Strings Without Encoding: Passing Python string objects directly to `hashlib.sha256()` without calling `.encode('utf-8')`.
3. Confusing Encryption with Signing: Claiming digital signatures "encrypt" transaction data. Signatures do NOT encrypt data; the data remains public while the signature provides integrity and authentication.
4. Trying to derive Private Key from Public Key: Misunderstanding the one-way nature of ECDLP.
5. Verifying with Wrong Parameters: Passing the modified data but using the tampered hash incorrectly formatted during Task 4.

Examiner Focus
--------------
- Cryptographic Rigor: Correct execution of SHA-256 and ECDSA signing routines.
- Parameter Flow: Ensuring the public key (not private key) is used for signature verification.
- Tamper Detection Demonstration: Clear visual proof that modifying data causes signature verification failure.
- Core Theory Mastery: Explaining the distinction between Data Integrity, Authentication, and Non-Repudiation.

------------------------- SECTION 1: HASH FUNCTIONS & SHA-256 ------------------

Q1. What is a cryptographic hash function?
A. A mathematical algorithm that takes an arbitrary-sized input payload and converts it into a deterministic, fixed-size bit array (digest).

Q2. What is the output size of SHA-256 in bits and hexadecimal characters?
A. 256 bits, which translates to 64 hexadecimal characters (since each hex character represents 4 bits).

Q3. What is the Avalanche Effect in hashing?
A. A property where changing even a single bit in the input message produces a completely different, uncorrelated hash digest (flipping roughly 50% of the output bits).

Q4. What is Collision Resistance?
A. The cryptographic property making it computationally impossible to find two distinct input messages $M_1 \neq M_2$ that produce the exact same hash output ($\text{Hash}(M_1) == \text{Hash}(M_2)$).

Q5. What is Pre-image Resistance?
A. The one-way property of hash functions making it computationally infeasible to invert a hash digest $H$ back into its original message $M$.

------------------------- SECTION 2: ASYMMETRIC KEYS & ECDSA -------------------

Q6. What is the difference between symmetric and asymmetric cryptography?
A. Symmetric cryptography uses one shared secret key for encryption and decryption; asymmetric cryptography uses a mathematically linked key pair: a private key (kept secret) and a public key (shared publicly).

Q7. What is ECDSA?
A. Elliptic Curve Digital Signature Algorithm: an asymmetric cryptographic algorithm that uses the algebraic structure of elliptic curves over finite fields to sign and verify digital signatures efficiently.

Q8. Which elliptic curve is used in Bitcoin and Ethereum?
A. Secp256k1 ($y^2 = x^3 + 7 \pmod p$).

Q9. How is a public key derived from a private key in ECC?
A. Through scalar point multiplication on the elliptic curve: $Q = d \times G$, where $d$ is the private key scalar and $G$ is the generator point.

Q10. Why is it impossible to reverse a public key to obtain the private key?
A. Because computing $d$ from $Q = d \times G$ relies on the Elliptic Curve Discrete Logarithm Problem (ECDLP), which is computationally intractable with current technology.

------------------------- SECTION 3: SIGNING & VERIFICATION ------------------

Q11. Which key is used to create a digital signature, and which key is used to verify it?
A. The Private Key is used to CREATE the digital signature; the Public Key is used to VERIFY the signature.

Q12. What two values make up a standard ECDSA digital signature?
A. A pair of 256-bit integers denoted as $(r, s)$.

Q13. Does digitally signing a transaction encrypt the transaction payload?
A. No. The transaction data remains unencrypted and readable by anyone. The signature is appended alongside the data to prove authenticity and integrity.

Q14. What parameters are required by the verification algorithm?
A. The original message/hash, the digital signature $(r, s)$, and the sender's public key $Q$.

------------------------- SECTION 4: INTEGRITY & SECURITY ---------------------

Q15. Why does signature verification fail when transaction data is tampered with?
A. Because tampering changes the payload, producing a completely different SHA-256 hash. When the verification algorithm evaluates the original signature against the new hash, the mathematical curve equality check fails.

Q16. What is Data Integrity in blockchain?
A. The assurance that transaction details (amounts, recipients, nonces) have not been altered or corrupted in transit or storage.

Q17. What is Authentication in blockchain?
A. Cryptographic proof that a transaction was created by the legitimate owner of the private key associated with the sending account address.

Q18. What is Non-Repudiation?
A. The property ensuring that a sender who signed a transaction cannot claim they did not send it, because only their secret private key could have produced a valid signature for their public key.

------------------------- SECTION 5: BLOCKCHAIN APPLICATIONS ------------------

Q19. How is an Ethereum address derived from a public key?
A. By taking the Keccak-256 hash of the uncompressed public key bytes (excluding 0x04 prefix) and extracting the last 20 bytes (40 hex characters) prepended with `0x`.

Q20. Why do we hash a message before digitally signing it?
A. Hashing converts variable-length transaction payloads into a fixed 256-bit length, making signature computation fast, predictable, and memory-efficient regardless of transaction size.

Q21. What happens if a private key is compromised or leaked?
A. An attacker possessing the private key can sign arbitrary transactions, steal funds, and impersonate the account owner completely. Security is irrevocably broken.

Q22. What is a nonce in the context of account transactions?
A. A sequential counter attached to an account's transactions to prevent Replay Attacks (re-submitting an identical valid signed transaction multiple times).
