PART B - THEORY: WHAT PROOF-OF-WORK IS AND WHY IT EXISTS
==============================================================================

B.1 Definition
--------------
Proof-of-Work (PoW) is a cryptographic consensus mechanism that requires network participants (miners)
to expend computational power solving a computationally hard but trivially verifiable puzzle in order
to add a new block to the blockchain.

B.2 The Core Problem PoW Solves
-------------------------------
In a distributed peer-to-peer network without a central authority:
1. Sybil Attacks: An attacker can create millions of virtual nodes at zero cost to overwhelm the network.
   PoW ties voting power to physical computational resources (hash power), making Sybil attacks cost-prohibitive.
2. Spam & Denial of Service (DoS): Without a cost for block creation, malicious actors could flood the ledger.
3. Consensus & Ordering: PoW provides an objective rule for deciding which version of history is valid when
   competing blocks are produced (the Longest / Heaviest Chain Rule).
4. Historical Immutability: Re-writing past transactions requires re-doing all the PoW for the tampered block
   AND every subsequent block.

B.3 Analogies for Proof-of-Work
-------------------------------
- The Lottery / Combination Lock: Finding a valid hash is like trying millions of combinations on a digital lock.
  You cannot predict which combination works; you can only try them one by one. Once unlocked, anyone watching
  can verify instantly that the key fits the lock.
- Scratch Cards: It takes time and money to scratch off thousands of cards until a winner is found, but anyone
  can instantly confirm a winning card upon inspection.

B.4 Properties of cryptographic puzzles in PoW
---------------------------------------------
1. Hard to Solve (Computationally Intensive): Requires brute-force search; no shortcuts exist.
2. Easy to Verify (Asymmetric Cost): Verification requires a single execution of the hash function.
3. Parameterizable / Adjustable Difficulty: The puzzle difficulty can be adjusted dynamically to maintain a
   stable block production time regardless of total network compute power.
4. Non-Progress Free (Memoryless): Every trial is independent (a Bernoulli trial). A miner who has tried
   1,000,000 nonces has the exact same probability of success on the next trial as a miner who just started.

PART C - THEORY: NONCE AND BLOCK HEADER STRUCTURE (TASK 1)
==============================================================================

C.1 Block Header Fields in PoW
------------------------------
In a PoW blockchain, the block header contains all metadata that must be hashed:

  index          : Position of the block in the chain (0, 1, 2, ...).
  timestamp      : Creation time of the block (unix timestamp or string).
  data           : The payload (transactions or Merkle root of transactions).
  previous_hash  : SHA-256 hash of the preceding block header.
  nonce          : Arbitrary counter field varied during mining.
  hash           : SHA-256 digest of all above header fields once target condition is met.

C.2 Role of the Nonce
---------------------
To find a hash that meets the target condition, the miner must hash a string that produces a specific bit pattern.
Since index, timestamp, data, and previous_hash are fixed for a given block candidate, the **nonce** is the only
field that the miner can freely change to generate a brand new, pseudorandom hash digest.

  hash = SHA-256( index + timestamp + data + previous_hash + nonce )

If the resulting `hash` does not satisfy the target, `nonce` is incremented:
  Iteration 1: nonce = 0    => SHA-256(...) = 8f4a... (Fail)
  Iteration 2: nonce = 1    => SHA-256(...) = 3c1b... (Fail)
  Iteration 3: nonce = 2    => SHA-256(...) = 0000a9d2... (Success!)

C.3 SHA-256 Properties Utilized in Mining
------------------------------------------
1. Deterministic: Same input string always produces the exact same 256-bit hash output.
2. Avalanche Effect: Changing a single bit in the input (e.g., incrementing nonce from 1 to 2) flips ~50%
   of the output bits unpredictably.
3. Pre-image Resistance: Given a target hash string, it is computationally impossible to invert SHA-256 to find
   the input nonce without brute forcing.
4. Uniform Distribution: SHA-256 output values are uniformly distributed across the $2^{256}$ search space.

C.4 Target Criteria Formulation
-------------------------------
In simplified lab settings, difficulty is defined as finding a hexadecimal hash string with $D$ leading zeros.
Examples:
  Difficulty D = 1  => Hash must match pattern: "0..."      (e.g., 0a3f...)
  Difficulty D = 4  => Hash must match pattern: "0000..."   (e.g., 00001f8c...)
  Difficulty D = 6  => Hash must match pattern: "000000..." (e.g., 0000004b...)

PART D - THEORY: MINING A BLOCK, HASH METRICS, AND OUTPUT REPORTING (TASK 2)
==============================================================================

D.1 Mining Algorithm Execution (Step-by-Step)
---------------------------------------------
1. Assemble Block Candidate: Gather `index`, `timestamp`, `data`, and `previous_hash`.
2. Set Mining Condition: Define `target_prefix = "0" * difficulty`.
3. Initialize Counter: Set `nonce = 0` and `attempts = 0`.
4. Capture Start Time: Record `start_time = time.time()`.
5. Mining Loop:
   a. Format input string: `input_str = str(index) + str(timestamp) + str(data) + str(previous_hash) + str(nonce)`.
   b. Compute SHA-256 digest: `current_hash = hashlib.sha256(input_str.encode()).hexdigest()`.
   c. Increment attempt counter: `attempts += 1`.
   d. Check condition: If `current_hash.startswith(target_prefix)` -> BREAK LOOP.
   e. Otherwise: `nonce += 1` and repeat loop.
6. Calculate Elapsed Time: `elapsed_time = time.time() - start_time`.
7. Calculate Hash Rate: `hash_rate = attempts / elapsed_time` (hashes per second).

D.2 Reporting Key Metrics
-------------------------
When presenting Task 2 to the examiner, four core parameters must be reported:
1. Winning Nonce: The exact numeric counter value that produced the valid hash.
2. Final Block Hash: The 64-character hexadecimal SHA-256 digest showing the required leading zeros.
3. Total Attempts / Iterations: The total number of hash calculations performed (equals `winning_nonce + 1`
   if starting from 0).
4. Execution Time: Wall-clock time spent in seconds, formatted to decimal places.

PART E - THEORY: DIFFICULTY SCALING AND COMPUTATIONAL EFFORT COMPARISON (TASK 3)
==============================================================================

E.1 Hexadecimal Search Probability
-----------------------------------
SHA-256 outputs a 256-bit hash, represented as 64 hexadecimal characters (0-9, a-f).
Each hex character represents 4 bits ($2^4 = 16$ possible values: 0, 1, 2, ..., f).

Probability of a single random hash starting with $D$ specific hex zeros:
  For 1 zero  (D=1): Probability P = 1 / 16 = 16^(-1) = 0.0625 (6.25%)
  For 2 zeros (D=2): Probability P = (1/16) * (1/16) = 16^(-2) = 0.00390625
  For 3 zeros (D=3): Probability P = 16^(-3) = 1 / 4,096
  For 4 zeros (D=4): Probability P = 16^(-4) = 1 / 65,536
  For D zeros     : Probability P = 16^(-D)

E.2 Expected Computational Effort Formula
-----------------------------------------
Since each nonce attempt is an independent trial with success probability $P = 16^{-D}$, the number of attempts
follows a **Geometric Distribution**. The expected (average) number of attempts $E[\text{tries}]$ is:

  E[tries] = 1 / P = 16^D

E.3 Empirical Scaling Table (Difficulty Comparison)
---------------------------------------------------
When running Task 3 across difficulties 1 to 6, observed iterations and execution time scale as follows:

  Difficulty (D) | Required Prefix | Expected Attempts (16^D) | Empirical Iterations | Execution Time (s) | Growth Factor
  ---------------+-----------------+--------------------------+---------------------+--------------------+--------------
  1              | "0"             | 16                       | 13                  | 0.0001 s           | Baseline
  2              | "00"            | 256                      | 199                 | 0.0006 s           | ~15.3x
  3              | "000"           | 4,096                    | 3,842               | 0.0098 s           | ~19.3x
  4              | "0000"          | 65,536                   | 74,220              | 0.1820 s           | ~19.3x
  5              | "00000"         | 1,048,576                | 1,289,402           | 3.1450 s           | ~17.3x
  6              | "000000"        | 16,777,216               | 18,943,211          | 46.2100 s          | ~14.7x

Key Insights:
- Exponential Growth: Each step increase in difficulty $D \rightarrow D+1$ increases computational effort and runtime
  by an average factor of **16**.
- Stochastic Variation: Actual iterations will fluctuate around $16^D$ because mining is probabilistic (Poisson process).
- Scale Thresholds: Difficulty 4 takes fractions of a second; Difficulty 6 takes nearly a minute; Difficulty 8
  would take hours on a single CPU core ($16^8 \approx 4.29 \text{ billion}$ attempts).

PART F - THEORY: MATHEMATICAL RELATIONSHIP BETWEEN TARGET, DIFFICULTY, AND EFFORT (TASK 4)
==============================================================================

F.1 The Numerical Target ($T$)
-----------------------------
In production blockchains like Bitcoin, difficulty is not defined as string prefix matching, but as a numeric value.
The 256-bit output of SHA-256 is treated as an integer between $0$ and $2^{256}-1$.

A block hash is valid if and only if its numerical value is strictly less than the target $T$:

  Integer( SHA-256(Block Header + Nonce) ) < Target (T)

F.2 Mathematical Definition of Difficulty ($D$)
----------------------------------------------
Difficulty $D$ is the relative measure of how hard a target $T$ is compared to the maximum allowed target $T_{\text{max}}$
(the target established for Genesis / Difficulty 1):

  Difficulty (D) = T_max / Target (T)

Where:
  T_max = Highest possible target (maximum target space, e.g., 0x00000000FFFF00000000000000000000... in Bitcoin).
  Target (T) = Current active threshold value enforced by the network.

F.3 Deriving the Inverse Relationship
-------------------------------------
From $D = T_{\text{max}} / T$, we rearrange to solve for Target $T$:

  Target (T) = T_max / Difficulty (D)

This yields the fundamental inverse relationship:
  1. Difficulty and Target are INVERSELY PROPORTIONAL ($D \propto 1/T$).
  2. As Difficulty INCREASES ($\uparrow$), Target DECREASES ($\downarrow$).
  3. A smaller Target ($T$) shrinks the valid target range within the $[0, 2^{256}-1]$ output space.
  4. A smaller target range means a lower probability $P$ of hitting a valid hash:
         P = Target / 2^256
  5. Lower probability $P$ requires higher expected mining effort $E$:
         Effort (E) = 1 / P = 2^256 / Target

F.4 Pipeline Summary Diagram
----------------------------
  Difficulty (D) Increases (↑)
           │
           ▼
  Target (T) Decreases (↓)
           │
           ▼
  Valid Hash Output Range Shrinks (↓)
           │
           ▼
  Success Probability P = (T / 2^256) Decreases (↓)
           │
           ▼
  Expected Attempts E = (1 / P) Increases Exponentially (↑)

F.5 Dynamic Difficulty Adjustment Rule
--------------------------------------
Blockchains implement difficulty adjustment algorithms to keep block creation times constant regardless of how many
miners join or leave the network.

Bitcoin Rule (Every 2016 Blocks, ~2 Weeks):
  Target_new = Target_old * ( Actual_Time_for_last_2016_blocks / Expected_Time_of_2_weeks )

- If Actual Time < Expected Time (Hash power joined) -> Target_new decreases -> Difficulty increases.
- If Actual Time > Expected Time (Hash power left)  -> Target_new increases -> Difficulty decreases.

G.1 Complete Python Implementation
----------------------------------
Below is a clean single-file script demonstrating all lab tasks:

```python
import hashlib
import time

class Block:
    def __init__(self, index, data, previous_hash="0"):
        self.index = index
        self.timestamp = time.time()
        self.data = data
        self.previous_hash = previous_hash
        self.nonce = 0
        self.hash = ""

    def calculate_hash(self):
        # Concatenate block fields and current nonce
        payload = f"{self.index}{self.timestamp}{self.data}{self.previous_hash}{self.nonce}"
        return hashlib.sha256(payload.encode('utf-8')).hexdigest()

    def mine_block(self, difficulty):
        target = "0" * difficulty
        attempts = 0
        start_time = time.time()

        while True:
            attempts += 1
            self.hash = self.calculate_hash()
            if self.hash.startswith(target):
                elapsed_time = time.time() - start_time
                return self.nonce, self.hash, attempts, elapsed_time
            self.nonce += 1

# Demonstration Pipeline
if __name__ == "__main__":
    print("=== TASK 1 & 2: MINING SINGLE BLOCK (Difficulty = 4) ===")
    b1 = Block(1, "Alice pays Bob 10 BTC", previous_hash="0000a1b2c3d4...")
    nonce, block_hash, attempts, elapsed = b1.mine_block(4)
    
    print(f"Winning Nonce    : {nonce}")
    print(f"Resulting Hash   : {block_hash}")
    print(f"Total Attempts   : {attempts}")
    print(f"Execution Time   : {elapsed:.4f} seconds")
    print(f"Hash Rate        : {attempts/elapsed:.2f} hashes/sec\n")

    print("=== TASK 3: DIFFICULTY COMPARISON BENCHMARK ===")
    print("Diff | Target Prefix | Attempts    | Time (s)   | Hash Rate (H/s)")
    print("-----------------------------------------------------------------")
    for d in range(1, 6):
        test_block = Block(2, "Test Data", previous_hash=block_hash)
        n, h, att, t_sec = test_block.mine_block(d)
        hr = att / t_sec if t_sec > 0 else 0
        print(f" {d}   | '{'0'*d}'{' '*(11-d)}| {att:<11} | {t_sec:<10.4f} | {hr:.2f}")
```

PART H - THEORY: SECURITY, 51% ATTACKS, AND HISTORICAL TAMPERING
==============================================================================

H.1 How PoW Protects Historical Immutability
---------------------------------------------
Consider a blockchain with 4 blocks: B0 -> B1 -> B2 -> B3.
Suppose an attacker attempts to modify transaction data in Block B1 (e.g., changing 10 BTC to 1000 BTC).

Step-by-step cascade effect under PoW:
1. Block B1's data changes -> Block B1's hash changes completely (avalanche effect).
2. The attacker re-computes B1's hash, but the old PoW nonce is no longer valid (hash no longer starts with required zeros).
3. The attacker MUST re-mine B1 (find a new winning nonce satisfying Difficulty D).
4. Block B2 stores `previous_hash = B1.hash`. Because B1's new hash changed, B2's `previous_hash` changes.
5. B2's hash changes -> B2's PoW becomes invalid.
6. The attacker MUST re-mine B2.
7. B3's `previous_hash` changes -> B3's PoW becomes invalid.
8. The attacker MUST re-mine B3.

Conclusion:
To alter an old block, the attacker cannot just change text; they must re-do the Proof-of-Work for the tampered block AND ALL SUBSEQUENT BLOCKS ($K, K+1, \dots, N$).

H.2 The Race Against Honest Miners
----------------------------------
While the attacker is busy re-mining historical blocks B1, B2, B3 on their private tampered fork, honest miners are continuously appending new blocks (B4, B5, B6...) to the public chain.

According to the **Longest Chain Rule** (or Heaviest Chain Rule), nodes will always prefer the valid chain with the most cumulative Proof-of-Work.
- To make the network accept the tampered chain, the attacker must re-mine all past blocks AND surpass the tip of the honest chain.
- To outpace the honest network, the attacker must control more computational hash power than all honest miners combined (> 51% of total network hash rate).

H.3 The 51% Attack
-------------------
A 51% attack occurs when an entity commands more than 50% of the total mining hash rate on a PoW network.

What a 51% Attacker CAN do:
- Reverse recent transactions they sent themselves (Double-Spending).
- Prevent other transactions from being confirmed (Denial of Service).
- Out-mine honest nodes and rewrite historical blocks back to the point where they gained majority control.

What a 51% Attacker CANNOT do:
- Forge digital signatures (cannot steal coins from arbitrary users' wallets).
- Change consensus rules or block rewards (honest nodes reject invalid blocks regardless of hash power).
- Change past transactions prior to the fork point without re-doing all work.

H.4 Confirmations
-----------------
A block is said to have $K$ confirmations if $K-1$ blocks have been mined on top of it.
- 1 Confirmation: Block included in tip.
- 6 Confirmations (Bitcoin standard): 6 blocks mined on top (~1 hour).
The probability of an attacker with $<50\%$ hash power successfully overriding a block falls exponentially with the number of confirmations $K$.

PART I - DESIGN DETAILS, EDGE CASES, AND HARDWARE/ASIC CONSIDERATIONS
==============================================================================

I.1 Exhaustion of 32-bit Nonce Space
------------------------------------
In original Bitcoin specifications, `nonce` is a 32-bit unsigned integer ($2^{32} \approx 4.29 \times 10^9$ possible values).
At modern network hash rates (hundreds of Exahashes/sec), a single modern ASIC miner runs through all $4.29$ billion nonces in less than a millisecond!

How miners handle nonce exhaustion:
1. Update `timestamp` (varies the hash string).
2. Modify `ExtraNonce`: A field located in the scriptSig of the Coinbase transaction (the transaction paying the block reward).
3. Modifying `ExtraNonce` changes the Coinbase transaction hash -> changes the Merkle Root -> completely resets the entire 32-bit nonce search space!

I.2 Hardware Evolution in Mining
--------------------------------
1. CPU Mining (2009): Standard computers executing SHA-256 in general-purpose x86 code (~1-10 Megahashes/sec).
2. GPU Mining (2010): Graphics cards executing thousands of parallel threads (~100-500 Megahashes/sec).
3. FPGA Mining (2011): Field Programmable Gate Arrays tailored for SHA-256 bitwise manipulation (~1-10 Gigahashes/sec).
4. ASIC Mining (2013-Present): Application-Specific Integrated Circuits hard-coded onto silicon microchips purely to evaluate SHA-256 round equations (~100-300 Terahashes/sec per hardware unit).

I.3 Energy Consumption and PoW Alternatives
-------------------------------------------
Because PoW requires physical computation, real-world mining consumes immense electrical power. This has driven adoption of alternative consensus mechanisms:
- Proof of Stake (PoS): Replaces computational work with locked financial stake (e.g., Ethereum proof-of-stake migration).
- Proof of Authority (PoA): Identity-based consensus used in permissioned chains.
- Proof of Space / Time: Storage capacity-based consensus.

PART J - COMMON MISTAKES AND EXAMINER FOCUS
==============================================================================

Common Mistakes
---------------
1. Forgetting to reset `nonce = 0` when commencing mining on a new block candidate.
2. Failing to include essential block header fields (`previous_hash` or `data`) in the hash string, making work trivial or unlinked.
3. String matching bugs: Checking if hash *contains* zeros (`"0000" in hash`) instead of checking *leading* zeros (`hash.startswith("0000")`).
4. Attempting unrealistic difficulties (e.g., Difficulty = 8 or 9) on a single CPU core, causing Python to hang indefinitely.
5. Misinterpreting Target and Difficulty: Stating that Difficulty and Target increase together (they are inversely proportional!).
6. Forgetting to convert string inputs to bytes before passing to `hashlib.sha256()`.

Examiner Focus
--------------
- Code Execution: Verifying the PoW loop executes without errors and halts when the target condition is met.
- Metric Verification: Checking that the reported nonce actually produces the reported hash with correct leading zeros.
- Scaling Comprehension: Ability to explain why execution time scales by $16\times$ per extra hex zero.
- Architectural Understanding: Explaining why verification is fast ($O(1)$) while mining is slow ($O(16^D)$).

PART K - VIVA QUESTIONS WITH ANSWERS (EXHAUSTIVE)

------------------------- SECTION 1: CORE CONCEPTS ---------------------------

Q1. What is Proof-of-Work?
A. Proof-of-Work is a consensus mechanism requiring nodes to solve a computationally expensive cryptographic puzzle (finding a nonce that produces a hash below a target) to validate transactions and add new blocks to the ledger.

Q2. What is a nonce?
A. Nonce stands for "Number used ONCE". It is an arbitrary field in a block header updated continuously by miners to produce varying SHA-256 hash outputs until a target difficulty criteria is met.

Q3. What is the block header?
A. The block header is the collection of metadata that gets hashed during mining. It includes the block index, timestamp, previous block hash, transaction data (or Merkle root), and the nonce.

Q4. Why is a nonce necessary in mining?
A. Transaction data, previous hash, index, and timestamp are fixed for a given block candidate. The nonce provides the variable input needed to produce brand new pseudorandom hash values without altering block contents.

Q5. How is the hash of a block calculated during mining?
A. By serializing all block header fields including the nonce into a byte string and passing it to the SHA-256 hash function: `SHA-256(index + timestamp + data + previous_hash + nonce)`.

------------------------- SECTION 2: TARGET & DIFFICULTY --------------------

Q6. What is the Target in blockchain mining?
A. The Target is a 256-bit number that sets the ceiling threshold for valid block hashes. A block hash is valid if its integer value is strictly less than the Target.

Q7. What is Mining Difficulty?
A. Difficulty is a scalar measure reflecting how hard it is to discover a valid hash relative to the maximum allowable target ($D = T_{\text{max}} / T$).

Q8. What is the mathematical relationship between Target and Difficulty?
A. They are inversely proportional: $D \propto 1/T$. When Difficulty increases, Target decreases, shrinking the acceptable output hash space.

Q9. In our Python lab, how was difficulty simplified?
A. Difficulty was defined as the required number of leading zero hexadecimal characters ($D$) at the start of the hash string.

Q10. How does adding 1 hexadecimal zero affect the search effort?
A. Each hex character represents 4 bits ($2^4 = 16$ possibilities). Requiring 1 additional leading zero reduces success probability by $1/16$ and increases expected hash attempts by 16 times ($16^D$).

------------------------- SECTION 3: COMPUTATIONAL EFFORT & TIMING -----------

Q11. Why is Proof-of-Work considered asymmetric?
A. Because solving the puzzle requires brute-forcing millions of attempts ($O(16^D)$ work), but verifying the solution takes a single hash calculation ($O(1)$ work).

Q12. What probability distribution governs PoW mining?
A. A Geometric distribution (or Bernoulli process of independent trials), where each nonce attempt has an identical, independent success probability $P = 16^{-D}$.

Q13. What is Hash Rate?
A. Hash rate is the speed at which a mining device computes SHA-256 hashes, measured in hashes per second (H/s, MH/s, GH/s, TH/s, EH/s).

Q14. Why do actual iterations in your lab differ from $16^D$?
A. Because mining is a probabilistic Poisson process; $16^D$ represents the mathematical mean (expected value), but individual runs fluctuate around this average.

------------------------- SECTION 4: SECURITY & CONSENSUS -------------------

Q15. How does PoW prevent historical block tampering?
A. Modifying an old block alters its hash and invalidates its PoW nonce. Because subsequent blocks store the hash of the preceding block, tampering breaks every link forward, forcing the attacker to re-mine the tampered block and all subsequent blocks.

Q16. What is the Longest Chain Rule?
A. The consensus rule stating that nodes must accept and extend the valid chain with the highest cumulative Proof-of-Work as the single source of truth.

Q17. What is a 51% Attack?
A. An attack where an entity controlling over 50% of total network hash power can out-mine honest nodes, allowing them to reverse recent transactions (double-spend) or censor transactions.

Q18. Can a 51% attacker steal arbitrary coins from other wallets?
A. No. A 51% attack grants hash power majority, not private key signatures. Honest nodes will reject transactions with invalid digital signatures regardless of hash rate.

Q19. What is a confirmation?
A. The number of blocks built on top of a specific block. More confirmations exponentially reduce the probability of the block being reversed by an attacker.

------------------------- SECTION 5: PRACTICAL & ADVANCED -------------------

Q20. What is nonce exhaustion and how is it solved in production?
A. A 32-bit nonce space contains $4.29$ billion combinations, which fast ASICs exhaust in milliseconds. Miners solve this by modifying the timestamp or changing the `ExtraNonce` field in the Coinbase transaction to reset the search space.

Q21. What is an ASIC?
A. Application-Specific Integrated Circuit: specialized hardware designed exclusively to compute SHA-256 hashing loops at extreme speed and energy efficiency.

Q22. Why does Bitcoin adjust mining difficulty dynamically?
A. To maintain a constant average block creation interval (~10 minutes) regardless of total global computational power joining or leaving the network.
