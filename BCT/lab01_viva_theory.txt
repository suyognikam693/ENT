##############################################################################
PART 1 : SHORT THEORY
##############################################################################

1.1 WHY MONITOR?
  Monitoring means regularly measuring CPU, memory, disk and network to spot
  problems before users do. Goals: availability, performance, capacity
  planning, and quick troubleshooting. The four core resources are CPU, memory,
  disk (space + I/O) and network. A "bottleneck" is the one resource that
  limits overall performance.

1.2 CPU AND LOAD AVERAGE
  CPU time is split into: us (user), sy (system/kernel), ni (nice), id (idle),
  wa (I/O wait), hi/si (interrupts), st (stolen by hypervisor).
  Load average = average number of processes that are running, ready to run, or
  in uninterruptible sleep (usually waiting for disk), shown for 1, 5 and 15
  minutes. Compare it with the number of cores (nproc): load > cores means
  queuing. Load and CPU% are different things - high load with low CPU often
  means disk wait.

1.3 MEMORY AND SWAP
  Linux uses spare RAM as cache (buff/cache), so "free" is naturally small.
  The "available" column is the real indicator. Swap is disk space used as
  overflow memory; heavy swapping (si/so in vmstat) makes the system very slow
  because disk is much slower than RAM.

1.4 DISK SPACE AND DISK I/O
  Two different problems: (a) SPACE - how full the filesystem is (df, du),
  also inodes (df -i); (b) I/O PERFORMANCE - how fast the disk serves requests
  (iostat, sar -d). Key I/O metrics: IOPS (r/s, w/s), throughput (kB/s),
  latency (await), queue length (aqu-sz), utilisation (%util).
  Linux reserves ~5% of ext4 space for root.

1.5 TOOLS AT A GLANCE
  uptime  - how long up, users, load averages (1/5/15 min)
  top     - live per-process view + CPU/memory summary (interactive)
  free    - RAM and swap totals
  df      - filesystem space usage
  vmstat  - virtual memory, processes, swap, I/O, CPU in one line per interval
  iostat  - CPU and per-device I/O statistics (sysstat package)
  sar     - collects/reports/saves system activity over time (sysstat package);
            can show history, unlike the others
  Interval syntax:  tool <seconds> <count>   e.g. vmstat 2 5 = 5 reports, 2 s apart.
  First report of vmstat/iostat = average since boot, not current.

1.6 BOTTLENECK PATTERNS
  CPU-bound   : high us/sy, low idle, run queue (r) > cores.
  Memory-bound: low available RAM, swap in/out active.
  Disk-bound  : low-ish CPU use, HIGH wa, blocked processes (b), high await,
                high %util, large queue. Load looks high though CPU is idle.

1.7 THRESHOLDS AND ALERTING
  A threshold is a value at which monitoring raises an alert. Usually two levels:
  WARNING (act soon) and CRITICAL (act now). Good thresholds are based on
  failure behaviour and give enough lead time. Use sustained values over
  several samples to avoid false alarms from short spikes.
  This lab: Disk space 85% warn / 95% crit;  CPU iowait 15% warn / 25% crit.

PART 2 : QUESTIONS WITH MODEL ANSWERS
##############################################################################

------------------------------------------------------------------------------
LEVEL A : LOWER-MODERATE (basic understanding)
------------------------------------------------------------------------------

Q1. What does the uptime command show?
A1. Current time, how long the system has been running, number of logged-in
    users, and the load averages for the last 1, 5 and 15 minutes.

Q2. Which command shows disk space usage and which option makes it human
    readable?
A2. df. Use df -h for human-readable sizes (KB/MB/GB).

Q3. In the output of free, which column should you look at to know how much
    memory is really available to applications?
A3. The "available" column (not "free").

Q4. What is the difference between top and ps?
A4. top is a live, refreshing view of processes and system summary; ps gives a
    one-time snapshot of processes.

Q5. How do you run top non-interactively to save its output in a file?
A5. top -b -n 1 > file.txt   (-b batch mode, -n number of iterations).

Q6. What does the command vmstat 2 5 do?
A6. Prints 5 reports, 2 seconds apart. The first report shows averages since
    boot.

Q7. Which package provides iostat and sar? How do you install it on Ubuntu?
A7. The sysstat package: sudo apt install sysstat.

Q8. What do us, sy, id and wa represent in the CPU line?
A8. us = user-space time, sy = kernel time, id = idle, wa = idle time waiting
    for I/O to complete.

Q9. What is swap space?
A9. Disk area used as extra memory when RAM is full; much slower than RAM.

Q10. What does a load average of 0.50, 0.70, 1.20 tell you about the trend?
A10. The 15-min value (1.20) is higher than the 1-min (0.50), so load has been
     DECREASING recently.

------------------------------------------------------------------------------
LEVEL B : MIDDLE-MODERATE (interpretation)
------------------------------------------------------------------------------

Q11. Your server has 4 cores and load average is 4.0. Is it overloaded?
A11. It is fully utilised but not necessarily overloaded; load equals core
     count. Sustained values above 4 (e.g. 8) mean processes are queuing.
     Also check whether the load is CPU or I/O related.

Q12. "free" shows only 200 MB free out of 8 GB. Is this a problem?
A12. Not necessarily. Linux caches files in unused RAM. Check "available"; if
     it is large (say 5 GB) the system is fine.

Q13. Why is the first line of vmstat/iostat output usually ignored?
A13. It reports the average since system boot, not the current activity, so it
     hides the present behaviour. Real samples start from the second report.

Q14. What do si and so columns in vmstat indicate? What value is healthy?
A14. si = memory swapped in from disk, so = memory swapped out to disk (KB/s).
     Healthy is zero or near zero; continuous non-zero values mean memory
     pressure.

Q15. What does the "b" column in vmstat mean?
A15. Number of processes in uninterruptible sleep, usually waiting for I/O. A
     persistently non-zero b suggests disk problems.

Q16. In iostat -x, what does %util represent and what does ~100% mean?
A16. Percentage of time the device was busy handling requests. Near 100% means
     the device is saturated (for single-queue disks); requests are waiting.

Q17. What is await in iostat? What are typical bad values?
A17. Average time (ms) an I/O request spends in queue plus being serviced.
     Roughly above 20 ms on SSD or above 50 ms on HDD, sustained, is bad.
     Newer versions split it into r_await and w_await.

Q18. Difference between iostat and sar?
A18. iostat reports CPU and device I/O for the interval you run it. sar can do
     much more (CPU, memory, network, queue, I/O) and can store and replay
     historical data from /var/log/sysstat.

Q19. Command to see CPU utilisation five times, every 2 seconds, using sar?
A19. sar -u 2 5

Q20. Why might df show 100% IUse% while Use% is low?
A20. Inodes are exhausted by a huge number of small files. Files can't be
     created even though space remains. Check with df -i.

Q21. What does the "st" value in top mean?
A21. Steal time: CPU time taken by the hypervisor for other virtual machines.
     High st on a VM means noisy neighbours / over-subscribed host.

Q22. How do you find the top memory-consuming processes in top?
A22. Press M inside top (sort by memory) or use top -o %MEM; also
     ps aux --sort=-%mem | head.

------------------------------------------------------------------------------
LEVEL C : HIGHER-MODERATE (analysis and reasoning)
------------------------------------------------------------------------------

Q23. Load average is 7.5 on a 4-core server, but CPU idle is 35% and wa is 55%.
     Is the CPU the bottleneck? Explain.
A23. No. CPU is mostly idle or waiting. Load counts processes in D state
     (waiting for disk), so the high load comes from I/O wait. The bottleneck
     is disk I/O. Confirm with iostat -x (high %util, await, queue) and
     vmstat (b > 0).

Q24. Given: us=88, sy=9, id=3, wa=0, r=12 (4 cores), available RAM 40%, %util
     of disk 8%. Identify the bottleneck.
A24. CPU. Idle is just 3%, user+system 97%, run queue 12 is 3x the core count,
     and memory and disk are fine.

Q25. Given: available RAM 3%, swap used 90% and growing, si/so large, wa
     moderate. What is happening and why is wa rising?
A25. Memory shortage. The system swaps heavily; swap I/O hits the disk so
     iowait rises as a side effect. Fix the memory problem (add RAM, fix leak,
     reduce workload), not the disk.

Q26. Why can a disk with low %util still give slow response?
A26. %util shows busy time, not latency. With SSD/NVMe parallelism %util can
     be misleading; check await and aqu-sz. Slowness may also come from
     network storage, locks or application issues.

Q27. Why is 85% a reasonable WARNING threshold for disk space and 95% CRITICAL?
A27. At 85% there is time to clean logs or add storage before problems. At 95%
     writes may fail, databases and logs break, and ext4 root-reserved space is
     nearly consumed. Disk fills are gradual, so an early warning is cheap.

Q28. Why is CPU iowait chosen as a monitoring metric rather than only CPU
     usage? Justify 15% and 25%.
A28. Plain CPU usage can look low while the system is stalled on storage.
     iowait reveals this. Above ~15% sustained, disk latency begins to hurt
     request times (warning); above ~25% a quarter of CPU capacity is lost
     waiting for disk and applications are visibly starved (critical).
     Thresholds should be sustained, since brief spikes are normal.

Q29. A vmstat sample shows r=1, b=0, wa=0, us=3, id=96. Users still complain
     the app is slow. Where do you look next?
A29. Not CPU, memory or disk. Check network (sar -n DEV, ss), application logs,
     database queries, locks, DNS, external dependencies.

Q30. Explain how you would prove that the bottleneck is storage using only the
     lab tools.
A30. 1) uptime: high load. 2) top: low us/sy but high wa. 3) vmstat: b>0, high
     wa and bi/bo. 4) iostat -x: %util near 100, high await, large aqu-sz.
     5) sar -b / -d: confirms tps and throughput. All pointing to the same
     device = disk I/O bottleneck.

Q31. Why can't we kill the process shown in D state?
A31. A D (uninterruptible sleep) process is waiting inside the kernel for I/O;
     signals, even SIGKILL, are not handled until the I/O completes. Fix the
     underlying storage issue.

Q32. What is the difference between throughput and latency in disk
     performance? Which matters more for a database?
A32. Throughput = amount of data per second (MB/s). Latency = time per request
     (ms). Databases doing many small random reads/writes are usually more
     sensitive to latency and IOPS.

Q33. Why use several samples (interval and count) rather than a single reading?
A33. A single reading may catch a spike or a quiet moment. Multiple samples
     show trends and give an average, so conclusions are more reliable.

Q34. If you must keep monitoring data for the whole day to analyse a past
     slowdown at 3 AM, which tool and what setup is required?
A34. sar with sysstat collection enabled (ENABLED="true" in
     /etc/default/sysstat, service running). Then: sar -u -s 02:50:00
     -e 03:10:00 (or -f /var/log/sysstat/saDD).

Q35. Give two ways to reduce an observed disk I/O bottleneck.
A35. Move to faster storage (SSD/NVMe), add RAM for page cache, move logs/DB
     to separate disks, reduce unnecessary logging, optimise queries and
     batch writes, use caching, spread load with RAID or more volumes.

------------------------------------------------------------------------------
QUICK-FIRE ONE-LINERS (rapid revision)
------------------------------------------------------------------------------
- Load vs cores              : compare load average with nproc
- Real free memory           : "available" column in free
- since-boot report          : first line of vmstat / iostat
- Disk saturation sign       : %util ~100, high await, big queue
- High load + low CPU        : suspect disk wait (D-state processes)
- sar history path           : /var/log/sysstat/
- Enable sar collection      : /etc/default/sysstat -> ENABLED="true"
- Batch mode top             : top -b -n 1
- Inode usage                : df -i
- Thresholds (this lab)      : disk 85/95 %, iowait 15/25 %
